# Simulation acceptance

Run the simulation journeys from the repository root with Node 24 and a running Docker daemon:

```sh
npm ci
npm run build:sdk && node tests/acceptance/simulations/moving-assets.mjs
npm run build:sdk && node --import ./simulations/node_modules/tsx/dist/loader.mjs tests/acceptance/simulations/observations-objects.mjs
npm run build:sdk && node --import ./simulations/node_modules/tsx/dist/loader.mjs tests/acceptance/simulations/multi-client-sync.mjs
npm run build:sdk && node --import ./simulations/node_modules/tsx/dist/loader.mjs tests/acceptance/simulations/observations-late-assertions.mjs
```

Each invocation starts a disposable Atlas Core, PostgreSQL, and MinIO stack. It then uses a test-only launcher to construct the actual simulations server factory on a loopback port reserved for each bounded startup attempt with the built workspace SDK. It retries only a recognized `EADDRINUSE` startup exit. The launcher loads its configuration and cleanup ledger from a runner-owned temporary package root, so it does not read or alter `simulations/.env` or its ledger. It links built simulation assets only when they already exist; these API-and-SDK journeys do not build or verify browser assets. The browser acceptance journey covers those assets. It records the actual isolated ledger path before fixture cleanup, verifies that exactly the `local` target is exposed without deployed credentials, and tears down only its generated Compose project and child process.

The moving-assets journey completes a bounded run and cancels a second after its first telemetry tick. A separate SDK client verifies persisted coordinates and speed without relying on simulation status. Before cleanup, it replaces a run-owned Entity and creates unrelated Entity and Object instances; cleanup must preserve those instances while removing run-owned Entities. After cancellation, fresh reads separated by one tick interval must show that telemetry no longer changes before cleanup removes each cancelled Entity. A test-only Core overlay also creates, delivers, completes, and independently rereads a nonempty Task after its run-owned Asset is cleaned up.

The observations-objects journey requires the original `POST /api/runs` summary and first replayed SSE event to report `running`, then independently reads observer Assets, track Entities, and their linked Objects after completion. Its complete created-resource set must contain exactly those observer and track Entities plus observation Objects. Objects from this scenario are metadata-only: `path`, `size_bytes`, `content_type`, and `bucket` must be null, rather than representing stored binary bytes. Numbered observer and track Entity IDs are mapped from their stable numeric component before every expected alias, coordinate, simulation metadata, relation, and completion-log linkage is compared; hash suffixes remain opaque. Each numbered observer must have exactly its own numbered `camera` sensor reference with a horizontal field of view of 60, heading 90, speed 4, and `observing` status. Tracks alternate `unknown` and `neutral` military classifications with `observed` status and valid telemetry and status update timestamps. Each numbered Object must have exactly `usage_hints: ["thumbnail"]` and one reference to its matching track. The test replaces run-owned Entity and Object instances before cleanup, preserves unrelated resources, and rereads those protected instances after both completed and cancelled cleanup. After a cancellation, it waits at least one configured tick and requires the resource set and observation logs to remain unchanged. The cancelled cleanup replay must contain the `Stop requested` log followed by its cancelled status event.

The multi-client-sync journey requires the original `POST /api/runs` summary and first replayed SSE event to report `running`, then starts separate SDK readers outside the simulation process. Polling is disabled so each reader must converge through the SDK feed. After reader startup and before writers are created, each reader's public fetch hook observes real transport calls; any post-startup SDK HTTP request makes the feed-only convergence check fail. It requires every run-created resource to be a writer Entity, and maps the stable numbered portion of each Entity ID before checking the matching alias, coordinates, `sync-probe` status, and write index while treating the hash suffix as opaque. It also requires the producer's ordered `Sync client N started` and `Writer created <id>` progress logs. Before cleanup it replaces one run-owned writer with a fresh instance token and creates unrelated Entity and Object canaries; fresh reads must show all three survive while every other run-owned Entity is removed. The canaries and replacement are deleted with their own tokens during test teardown. This is an SDK feed-convergence and ownership check independent of the scenario's internal readers and assertions.

Both journeys load the browser's `parseRunEvent` directly for every raw SSE frame and mirror its private API summary guard for the initial, completed, and cleanup summaries they consume. Observations also consumes its stop and cancelled summaries; multi-client sync covers its completed cleanup path only. Their descriptors retain the stable scenario ID, exact typed input contract, and nonempty user-visible name, summary, and input labels; this behavior acceptance does not snapshot editorial wording. The original `POST` summary must be running, uncleaned, and have empty resource and assertion collections. Every summary is bound to its advertised scenario name, requested local target, and, after start, run ID, original deterministic input values, and optional JSON input. The initial `startedAt` remains fixed across reads, and a terminal `finishedAt` remains fixed through cleanup. The input comparison permits only 32-ULP number representation noise from server step alignment; keys, non-numeric values, and JSON remain exact. This requires canonical event timestamps, typed event payloads, and structurally valid browser API summaries while preserving the raw stream artifact if validation fails. The journeys require complete unique numbered assertion IDs and the expected name/pass set. Multi-client reader completions may occur in either order, so its replay and summary must preserve the same actual ID/name/pass mapping instead of an assumed reader-to-ID ordering. They keep summaries uncleaned before explicit cleanup and require cleanup summaries to report `cleaned: true`; their scenario-specific expected values remain separate checks.

Expected-success replays require the requested run ID on every event and no error events. A completed replay has one final `completed` status after all resource, log, and assertion evidence; cleanup has one final `Cleanup complete` marker after every per-resource cleanup message. Replay and summary assertions must retain their independent input-derived ID, name, pass result, and message set, as well as matching each other. The cancellation journey derives whether verifier assertions are possible from the post-stop replay prefix through the cancelled marker: before every observation pair it permits only an empty assertion set, otherwise only empty or the complete source-valid verifier set. It preserves results observed before the stop, requires each stop result to persist to the cancelled read, and binds that read to the post-stop replay. Every lifecycle target has exactly the five public fields (`id`, `label`, `baseUrl`, `deployed`, and `apiKeyConfigured`), so credential-bearing extras cannot enter recorded evidence.

Every invocation writes the exact revision, dirty-worktree state, duration, expected and observed values, raw SSE frames and parsed events even when stream opening fails, simulation HTTP responses with a 35-second cleanup deadline and 15-second deadline for other requests, server output, and Compose logs under `.atlas/acceptance/simulations-<scenario>/`. The observations-objects and multi-client-sync completed and cleanup replays require one matching run ID with strictly increasing event sequences and an SSE frame deliverable to the browser's default `onmessage` handler. Cleanup requires exactly one `Cleanup complete` marker after every per-resource cleanup message, because the browser closes the stream at that marker. Set `ATLAS_ACCEPTANCE_ARTIFACTS` to choose another artifact root.

`observations-late-assertions` is an active, intentionally failing regression case for the cancelled-run assertion defect documented in [`docs/problems/2026-09-13-cancelled-run-late-assertions.md`](../../../docs/problems/2026-09-13-cancelled-run-late-assertions.md). It uses the existing target client-factory seam to pause the real verifier's first read until that reader's stop signal aborts. The browser-equivalent stream then closes on `cancelled`; the test fails when a later summary contains assertions that the terminal stream could not surface. The normal observations journey continues to run with the unwrapped production client factory.

The required `Simulation scenario acceptance` workflow runs observations-objects, multi-client-sync, and the active observations-late-assertions regression case in separate jobs and uploads required evidence. The first two jobs are expected to remain green; the late-assertions job stays red until its documented product defect is repaired. Its nightly or manually dispatched matrix runs the two normal scenarios independently with `ATLAS_ACCEPTANCE_NIGHTLY=1`: it expands observations to three observers and eight observations, multi-client sync to four clients and eight writes, and records each scenario's invalid-cardinality public-input fault. The workflow keeps push, scheduled, and manual runs in separate concurrency groups, so a push does not cancel a nightly run. Those configured nightly paths require hosted execution; the local required runs only prove the recorded host and Docker daemon environment.
