# Simulation acceptance

Run the simulation journeys from the repository root with Node 24 and a running Docker daemon:

```sh
npm ci
npm run build:sdk && node tests/acceptance/simulations/moving-assets.mjs
npm run build:sdk && node --import ./simulations/node_modules/tsx/dist/loader.mjs tests/acceptance/simulations/observations-objects.mjs
npm run build:sdk && node --import ./simulations/node_modules/tsx/dist/loader.mjs tests/acceptance/simulations/multi-client-sync.mjs
```

Each invocation starts a disposable Atlas Core, PostgreSQL, and MinIO stack. It then uses a test-only launcher to construct the actual simulations server factory on a loopback port reserved for each bounded startup attempt with the built workspace SDK. It retries only a recognized `EADDRINUSE` startup exit. The launcher loads its configuration and cleanup ledger from a runner-owned temporary package root, so it does not read or alter `simulations/.env` or its ledger. It links built simulation assets only when they already exist; these API-and-SDK journeys do not build or verify browser assets. The browser acceptance journey covers those assets. It records the actual isolated ledger path before fixture cleanup, verifies that exactly the `local` target is exposed without deployed credentials, and tears down only its generated Compose project and child process.

The moving-assets journey completes a bounded run and cancels a second after its first telemetry tick. A separate SDK client verifies persisted coordinates and speed without relying on simulation status. Before cleanup, it replaces a run-owned Entity and creates unrelated Entity and Object instances; cleanup must preserve those instances while removing run-owned Entities. After cancellation, fresh reads separated by one tick interval must show that telemetry no longer changes before cleanup removes each cancelled Entity. A test-only Core overlay also creates, delivers, completes, and independently rereads a nonempty Task after its run-owned Asset is cleaned up.

The observations-objects journey requires the original `POST /api/runs` summary and first replayed SSE event to report `running`, then independently reads observer Assets, track Entities, and their linked Objects after completion. Its complete created-resource set must contain exactly those observer and track Entities plus observation Objects. Objects from this scenario are metadata-only: `path`, `size_bytes`, `content_type`, and `bucket` must be null, rather than representing stored binary bytes. Numbered observer and track Entity IDs are mapped from their stable numeric component before every expected alias, coordinate, simulation metadata, relation, and completion-log linkage is compared; hash suffixes remain opaque. Each numbered observer must have exactly its own numbered `camera` sensor reference with a horizontal field of view of 60, heading 90, speed 4, and `observing` status. Tracks alternate `unknown` and `neutral` military classifications with `observed` status. Each numbered Object must have exactly `usage_hints: ["thumbnail"]` and one reference to its matching track. The test replaces run-owned Entity and Object instances before cleanup, preserves unrelated resources, and rereads those protected instances after both completed and cancelled cleanup. The cancelled cleanup replay must contain the `Stop requested` log followed by its cancelled status event.

The multi-client-sync journey requires the original `POST /api/runs` summary and first replayed SSE event to report `running`, then starts separate SDK readers outside the simulation process. Polling is disabled so each reader must converge through the SDK feed. After reader startup and before writers are created, each reader's public fetch hook observes real transport calls; any post-startup SDK HTTP request makes the feed-only convergence check fail. It requires every run-created resource to be a writer Entity, and maps the stable numbered portion of each Entity ID before checking the matching alias, coordinates, `sync-probe` status, and write index while treating the hash suffix as opaque. It requires the producer's exact four public assertion names for each numbered simulated client. Before cleanup it replaces one run-owned writer with a fresh instance token and creates unrelated Entity and Object canaries; fresh reads must show all three survive while every other run-owned Entity is removed. The canaries and replacement are deleted with their own tokens during test teardown. This is an SDK feed-convergence and ownership check independent of the scenario's internal readers and assertions.

Both journeys load the browser's `parseRunEvent` directly for every raw SSE frame and mirror its private API summary guard for the initial, completed, cancelled, and cleanup run summaries they consume. This requires canonical event timestamps, typed event payloads, and structurally valid browser API summaries while preserving the raw stream artifact if validation fails. The journeys also require unique numbered assertion IDs, keep summaries uncleaned before explicit cleanup, and require cleanup summaries to report `cleaned: true`; their scenario-specific expected values remain separate checks.

Every invocation writes the exact revision, dirty-worktree state, duration, expected and observed values, raw SSE frames and parsed events even when stream opening fails, simulation HTTP responses with a 35-second cleanup deadline and 15-second deadline for other requests, server output, and Compose logs under `.atlas/acceptance/simulations-<scenario>/`. The observations-objects and multi-client-sync completed and cleanup replays require one matching run ID with strictly increasing event sequences. Set `ATLAS_ACCEPTANCE_ARTIFACTS` to choose another artifact root.

The required `Simulation scenario acceptance` workflow runs observations-objects and multi-client-sync in separate jobs and uploads required evidence. Its nightly or manually dispatched matrix runs each scenario independently with `ATLAS_ACCEPTANCE_NIGHTLY=1`: it expands observations to three observers and eight observations, multi-client sync to four clients and eight writes, and records each scenario's invalid-cardinality public-input fault. The workflow keeps push, scheduled, and manual runs in separate concurrency groups, so a push does not cancel a nightly run. Those configured nightly paths require hosted execution; the local required runs only prove the recorded host and Docker daemon environment.
