Atlas Protocol

The foundational contract layer for Atlas — one definition of what the data is.

Direction · implementation prep complete

Atlas Protocol is a central, foundational package that lives outside Atlas Core and above it. It owns the data structures and the rules for verifying them. Today that knowledge is spread by hand across validators, model accessors, serializers, docs, and example JSON — and those copies drift. The protocol collapses all of it into a single source of truth that every other package projects from.

01Why this exists

The shape of an entity, task, or object, and the rules for a valid component (telemetry, geometry, media_refs roles, RFC3339 timestamps, command-as-object-or-string) currently has no single home. It is re-stated in Go validation code, in the model layer, in serializers, in database-structure docs, and in example files. Each restatement is a chance to drift, and downstream consumers — notably the frontend — get no contract at all and are left guessing at our JSON shapes.

02What we want it to do

Be the single source of truth for the data model

Define entities, tasks, objects, and their components once, with their constraints, in one place.

Generate code instead of us hand-writing it

Produce Go types and validators from the definitions so Atlas Core's handwritten validation and known-key tables become generated artifacts, not maintained-by-hand copies.

Give every language the same contract

One definition → Go for the backend, TypeScript for the frontend, and (optionally) OpenAPI for the HTTP surface. The frontend stops guessing.

Push verification to the edges

The same schema can back app-level validation and a database boundary (JSON Schema → Postgres checks), so integrity no longer depends on every writer going through one Go code path.

Detect generated drift

A generated revision stamp or content hash tells us whether checked-in artifacts were produced from the current CUE source. It is a freshness check, not backwards-compatible protocol versioning.

03The boundary that keeps it clean

The protocol defines shape and contract. Atlas Core keeps behavior. If the protocol ever imports a database driver or knows about HTTP, the line has been crossed.

Protocol owns

  • Data structures & field types
  • Valid component keys & enums
  • Constraints (ranges, formats, required)
  • Cross-language type generation
  • Generated artifact freshness

Core keeps

  • Transactions & row locking
  • Merge semantics & read-modify-write
  • Task lifecycle / status transitions
  • Auth, HTTP, storage wiring
  • Pagination & query execution

04How we'd grow into it

Incrementally, lowest-risk first — this is a direction, not a big-bang rewrite:

  • Start by generating Core's validators and typed structs — the parts that drift from docs today.
  • Keep behavior (merge logic, lifecycle, transactions) handwritten in Core for now.
  • Add the TypeScript projection once the Go side proves the model.
  • Consider database-level validation after the contract has settled.

05Readiness decisions

  • First slice: entity blob plus telemetry and geometry components.
  • Generated-code workflow: output is checked in and never hand-edited; the protocol check command fails when artifacts drift from CUE.
  • Later slices: task, object, TypeScript validators, OpenAPI fragments, and database checks.
Scope note: as Atlas Protocol becomes real, project-level decisions and blockers move with it. Design decisions and problems now live at the project root (docs/design-decisions/, docs/problems/) precisely because they span Atlas Core, Atlas Protocol, and whatever comes next — they are no longer Core-only.
