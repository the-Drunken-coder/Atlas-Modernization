# Meshtastic radios use one locally enforced profile

1. **Time and date:** 2026-09-02, America/New_York
2. **Name:** Every Link service applies one common static Radio profile to its attached radio
3. **Context:** Atlas owns every radio and runs the same Meshtastic Link software behind each one. Gateway and Asset behavior belongs to the companion computer, while remote radio configuration would depend on the same flaky mesh that a configuration change could disrupt.
4. **Decision:** Every supported radio uses one identical static Radio profile with no Gateway, Asset, per-device, or per-hardware overlays. The profile defines modem, relay, public rendezvous, module, and private-channel slot settings but contains no private-channel key. Dynamic Link membership is a separate input. Asset mode clears prior membership before discovery and obtains current membership through public-key-encrypted joining. Gateway mode loads durable Gateway-owned membership and never joins through itself. Each Link service reads, converges, and verifies only its locally attached radio. Gateway versus Asset remains a software mode outside the radio. Remote radio administration over Meshtastic is a non-goal. The Link service exposes one validated configuration system through a command-line interface and loopback programmatic API. Automatic firmware flashing is outside the initial scope. The initial firmware floor is Meshtastic 2.7.15, with one exact tested patch release selected for deployment.
5. **Alternatives considered:** Role-specific radio profiles were rejected because the radio performs the same mesh function behind either companion-computer role. Hardware overlays were rejected because they create configuration snowflakes; hardware unable to satisfy the common profile is unsupported. Remote administration was rejected because a flaky or partially reconfigured mesh is not a dependable management path. Direct CLI access to the serial port was rejected because it would compete with the running Link service.
6. **Consequences:** Radio behavior becomes reproducible across the fleet and configuration experiments can be associated with one exact profile. Gateway membership and explicit key rotation need durable local state outside the profile. Hardware support requires proving the common settings. Profile distribution happens through companion-computer software or configuration deployment rather than mesh administration. The CLI and programmatic API must share validation and evidence with startup convergence. Device keys, identity, calibration, GPIO, and other undeclared hardware state remain outside the common profile. Three physical radios must prove public-key-encrypted joining through one `LOCAL_ONLY` relay before field use.
7. **Location:** `docs/atlas-meshtastic-link/radio-configuration.md`, `docs/atlas-meshtastic-link/service-interface.md`, and the future Meshtastic Link service and CLI
