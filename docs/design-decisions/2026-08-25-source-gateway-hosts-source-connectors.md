# A private Source Gateway hosts Source connectors

1. **Time & Date:** 2026-08-25 11:18 EDT
2. **Name:** External-source access runs in one private Source Gateway container
3. **Context:** Source connectors need credentials and outbound network access. Hosting them in Core would put external traffic and failure load in the control plane. Giving credentials to each Plugin would duplicate secret handling, host policy, rate limits, and caching.
4. **Decision:** One private Source Gateway container hosts named Source connectors for all Plugins. It is part of the Compose-managed Atlas deployment and exposes no public API. Deployment configuration defines connector IDs, external origins, limits, and secret references. The Gateway resolves secrets from environment variables or Compose secrets at startup. Each connector pins its external origin and credentials. A Plugin identifies a connector and submits a relative path, method, query, allowed headers, and body within configured limits. The Gateway rejects absolute URLs, origin overrides, and credential-header overrides. It buffers the complete upstream response under a per-connector response-size limit that cannot exceed a hard Gateway maximum, then returns the upstream status, allowed response headers, and raw response bytes. It rejects oversized responses without returning partial bodies. Caching is disabled by default. A connector may enable a disposable in-memory time-to-live cache keyed by the complete outbound request. Connector configuration also declares which request methods and upstream statuses are safe to retry. The Gateway performs only bounded retries under those rules and maintains one circuit breaker per connector. The Gateway returns fixed failure categories for an unknown connector, rejected request policy, timeout, oversized response, open circuit, and unreachable upstream. It does not expose raw network or connector errors. A valid upstream HTTP response remains a response for the Plugin to interpret, even when its status represents a vendor error. Every installed Plugin may use every configured connector; connector access is not a Plugin capability. Plugins never receive source credentials, and Core does not proxy external-source traffic.
5. **Alternatives considered:** Core-hosted connectors were rejected because an optional external source should not consume Core resources or expand its failure modes. Direct Plugin access was rejected because each Plugin would need credentials and would reimplement shared access policy. Per-Plugin connector sidecars were rejected because they duplicate processes and cannot share provider rate limits or caches. Vendor-specific connector operations were rejected because the Gateway owns access mechanics rather than external data meaning. Arbitrary absolute URLs were rejected because they would turn the Gateway into an unrestricted outbound proxy. Per-Plugin connector grants were rejected because the initial deployment trusts every installed Plugin and has one developer.
6. **Consequences:** Gateway failure degrades source-dependent Plugins without changing Core liveness or readiness. Connector configuration changes restart the Gateway and clear its cache and circuit-breaker state. Core and Atlas resources never store External source credentials. Plugins can interpret JSON, XML, images, or other bounded payloads without adding vendor data models to the Gateway. Buffering makes rejection and caching simple but caps the practical response size. Retries occur only when deployment configuration explicitly marks them safe. Stable failure categories let Plugins handle access failures without depending on operating-system or HTTP-client messages. The architecture specifies hard bounds and behavior, while implementation chooses and tests response limits, cache durations, retry counts, and circuit-breaker thresholds. Adding untrusted Plugins would require this decision to be superseded with connector authorization.
