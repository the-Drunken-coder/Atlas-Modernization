# Core connects to explicitly configured Plugins over HTTP

1. **Time & Date:** 2026-08-25 11:05 EDT
2. **Name:** Deployment configuration and a fixed private HTTP/JSON protocol connect Core to Plugins
3. **Context:** Core must locate Plugin containers and invoke them without gaining Docker control or depending on startup order. The options are explicit configuration, Plugin self-registration, network discovery, or inspecting the container runtime. Core and Plugins also need one private transport contract.
4. **Decision:** Deployment configuration maps each stable Plugin ID to one private base URL. Core communicates with that endpoint through a fixed HTTP/JSON contract for manifest, health, and synchronous Operations. Core applies a hard response-size limit to every private call. An oversized manifest, health, or Operation response is invalid and makes the Plugin unavailable without Core buffering beyond the limit. Core fetches the manifest during startup, retries until the first success without blocking Core startup, and requires its Plugin ID to match deployment configuration exactly. An ID mismatch is invalid and is never cached. Core caches a valid matching manifest in memory until Core restarts. It does not refresh manifests periodically or fetch one per request. Every configured Plugin remains visible as `starting`, `available`, or `unavailable`. Authenticated status includes the latest check time and a stable Core-owned reason code. It does not include private URLs, raw health responses, credentials, or upstream response bodies. Core checks health on one fixed internal cadence. A connection failure, a manifest or health timeout, or an invalid private response makes the Plugin transport unavailable immediately. Any subsequent valid manifest, health, or Operation response restores transport availability immediately, even when the Operation rejects its input or health remains non-OK. A descriptor deadline affects only that Operation invocation. Transport recovery does not clear an application-level health failure; only a later OK health response does. Core maps non-OK health to the stable public reason `application_unhealthy` without exposing private detail. A cached manifest remains discoverable during an outage, but invocation fails. The Plugin contract has no revision field, version negotiation, or compatibility layer. Plugins do not self-register, and Core does not scan the network or Docker. Plugin availability does not change base liveness or readiness. The existing Atlas Protocol revision check remains part of Plugin SDK calls to Core, not the private Plugin protocol.
5. **Alternatives considered:** Self-registration was rejected because it makes ownership and stale registrations harder to reason about. Network or Docker discovery was rejected because it adds orchestration behavior and privileges to Core. A second transport such as gRPC was rejected because the initial control contract does not need another protocol stack.
6. **Consequences:** Plugin wiring is explicit and reviewable in deployment configuration. Startup order does not matter. A wrong configured URL cannot make Core accept another Plugin's identity. Plugin upgrades restart Core before a changed manifest takes effect. Core and Plugin changes update the private contract directly, and Plugin tests must catch incompatibility. Transport availability reacts immediately to failures and later valid responses, while an application-level health failure remains authoritative until the next successful health check. Status is useful for operators without leaking private deployment or vendor data. Implementation chooses and tests the health-check interval, response limits, and transport recovery. Hot installation and multiple active endpoints for one Plugin ID remain outside the first version.
7. **Location:** `docs/atlas-plugins/`, `atlas_core/`, future Plugin container contract and Compose configuration
