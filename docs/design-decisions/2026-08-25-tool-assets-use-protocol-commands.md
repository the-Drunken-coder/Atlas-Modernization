# Tool Assets use Protocol-owned Commands

1. **Time & Date:** 2026-08-25 11:05 EDT
2. **Name:** Taskable Plugins appear as optional Tool Assets and use dedicated Atlas Commands
3. **Context:** Some Plugins only answer Operations, while others need an operator to start or stop behavior through Atlas tasking. Current Atlas tasking targets Asset Entities, validates runtime manifests against the Protocol-owned production Command Catalog, and requires a purpose-built Command Interface input.
4. **Decision:** A taskable Plugin derives one stable Tool Asset ID from its Plugin ID and performs an idempotent get-or-create through its full-access Atlas SDK client during startup. It creates a missing Entity, reuses an existing `asset` with subtype `tool`, and refuses runtime registration if that ID belongs to anything else. If an operator deletes the Tool Asset after its Tasks become terminal, the Plugin recreates it at its next startup. Removing deployment configuration is the only Plugin uninstall path. Query-only Plugins do not register a Tool Asset. Tool Assets receive Tasks through the normal Asset runtime. Their commands are dedicated, Protocol-authored Atlas Commands; a Plugin manifest may advertise implemented catalog commands but cannot define new commands. A long-running Plugin Task may use `immediate` scheduling so several Tasks overlap. It remains `in_progress` while the behavior runs, declares `supports_cancel: true`, and uses Task cancellation as its stop action. Core marks cancellation terminal and aborts the matching handler without waiting for shutdown confirmation. Runtime replacement fails every active Task with `asset_restarted`; the Plugin never resumes it automatically.
5. **Alternatives considered:** Making every Plugin an Asset was rejected because bounded query Plugins are not task targets. Deployment-owned or Core-created Tool Assets were rejected in favor of Plugin startup through the SDK. Dynamically adding commands from Plugin manifests was rejected because it conflicts with catalog validation, safety review, generated types, and purpose-built operator inputs. Routing long-running control through Operations alone was rejected because it would bypass the existing Task lifecycle. Completing a Task after it merely configures durable state was rejected because the operator wants the active Task to represent the running behavior.
6. **Consequences:** Taskable Plugin behavior participates in normal scheduling, cancellation, runtime fencing, and Task history. Adding a new taskable capability requires a coordinated Atlas release across Protocol, the Plugin handler, and the Command Interface. Installing a Plugin alone cannot extend the Command Catalog. A monitoring Task is the only authority for its session, so planned upgrades and crashes stop monitoring and require an operator to create a new Task. Tool Asset deletion does not control deployment state.
7. **Location:** `docs/atlas-plugins/`, `atlas_protocol/commands/`, `atlas_core/internal/actions/`, `atlas_command_interface/`
