# Tool Assets use Protocol-owned Commands

1. **Time & Date:** 2026-08-25 11:05 EDT
2. **Name:** Taskable Plugins appear as optional Tool Assets and use dedicated Atlas Commands
3. **Context:** Some Plugins only answer Operations, while others need an operator to start or stop behavior through Atlas tasking. Current Atlas tasking targets Asset Entities, validates runtime manifests against the Protocol-owned production Command Catalog, and requires a purpose-built Command Interface input.
4. **Decision:** A taskable Plugin derives its Tool Asset ID as `plugin_` followed by the unpadded RFC 4648 base64url encoding of the SHA-256 digest of the exact ASCII Plugin ID. The prefix and full 43-character digest encoding fit the Protocol's 50-character Entity ID limit without normalization or truncation. The Plugin performs an idempotent get-or-create through its full-access Atlas SDK client during startup. If its private manifest advertises that ID, Core requires it to match the same derivation. The Plugin creates a missing Entity as an `asset` with subtype `tool` and a `custom_plugin` ownership component containing its Plugin ID. It reuses an existing Entity only when its type, subtype, and ownership marker all match. The ownership check also rejects the theoretical case where different Plugin IDs derive the same Entity ID. Any mismatch makes the Plugin refuse runtime registration and return non-OK private health. The Plugin platform extends Core's current runtime identity guard so `entity_type`, `subtype`, and the ownership marker cannot change after an Asset runtime has registered. Core rejects deletion of a Plugin-owned Tool Asset while its Plugin remains configured, in addition to the existing deletion guard for nonterminal Tasks. Removing deployment configuration is the only Plugin uninstall path; after removal and Task terminalization, an operator may delete its Tool Asset. Query-only Plugins do not register a Tool Asset. Tool Assets receive Tasks through the normal Asset runtime. Their commands are dedicated, Protocol-authored Atlas Commands; the Tool Asset runtime manifest may advertise implemented catalog commands but cannot define new commands. When a Command definition omits scheduling, Core uses the stored runtime manifest entry as the Asset's choice; a declared catalog value takes precedence and must match. Core uses that resolved scheduling for validation, Task creation, delivery, acknowledgement and start transitions, ordering, and immediate-start timeout reconciliation. A long-running Plugin Task may therefore use `immediate` scheduling so several Tasks overlap. It remains `in_progress` while the behavior runs, declares `supports_cancel: true`, and uses Task cancellation as its stop action. Core marks cancellation terminal and aborts the matching handler without waiting for shutdown confirmation. A deliberate runtime stop fails every active Task with `asset_stopped`; runtime replacement uses `asset_restarted`. If a process exits and no replacement registers, accepted Tasks remain nonterminal until an operator cancels them. The Plugin never resumes any of these Tasks automatically.
5. **Alternatives considered:** Making every Plugin an Asset was rejected because bounded query Plugins are not task targets. Deployment-owned or Core-created Tool Assets were rejected in favor of Plugin startup through the SDK. Dynamically adding commands from Plugin manifests was rejected because it conflicts with catalog validation, safety review, generated types, and purpose-built operator inputs. Routing long-running control through Operations alone was rejected because it would bypass the existing Task lifecycle. Completing a Task after it merely configures durable state was rejected because the operator wants the active Task to represent the running behavior.
6. **Consequences:** Taskable Plugin behavior participates in normal scheduling, cancellation, runtime fencing, and Task history. Adding a new taskable capability requires a coordinated Atlas release across Protocol, the Plugin handler, and the Command Interface. Installing a Plugin alone cannot extend the Command Catalog. The Plugin platform implementation must correct every Core lifecycle path that currently defaults omitted catalog scheduling to `queued`; changing manifest registration validation alone is insufficient. A monitoring Task is the only authority for its session, so planned upgrades and crashes stop monitoring and require an operator to create a new Task. A planned upgrade reports `asset_stopped` when graceful runtime stop completes; a replacement after an ungraceful stop reports `asset_restarted`. Without either transition, operational recovery must surface the stranded Tasks for operator cancellation. The immutable ownership marker prevents an existing unrelated Tool Asset from being reused accidentally. Deployment configuration, not Tool Asset deletion, controls whether the Plugin is installed.
