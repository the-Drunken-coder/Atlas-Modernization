# Map window workspace

1. **Time & Date:** 2026-08-31 19:40 EDT
2. **Name:** One workspace owns concurrent map-window layout
3. **Context:** The first map results inspector introduced a movable, collapsible window, but each window owning its own position cannot coordinate overlap, z-order, docking, or future concurrent panels. Operators also need a compact way to retain panels without covering the map.
4. **Decision:** The map stage has one `MapWindowWorkspace`. Feature code declares windows with stable identifiers and retains ownership of their content and close behavior. The workspace owns floating position, collapse, activation order, and four ordered dock rails. A window can be dragged to an insertion point on the top, right, bottom, or left edge; docked windows become ordered rail tabs and may pop back over the map. At most one window is popped out from each edge, while different edges and floating windows remain concurrent. Pointer and keyboard operations use the same state transitions.
5. **Alternatives considered:** Independent window-local state was rejected because it cannot coordinate edge order or concurrent popouts. A fixed split-pane workbench was rejected because it permanently reduces map area. A single minimized shelf was rejected because it loses the spatial relationship between a stored window and the edge from which it returns.
6. **Consequences:** New map windows must render inside the workspace and supply a stable ID. Workspace layout is currently session-local and resets when the map remounts. Docking behavior is centralized and can later support persistence without changing feature panels. The four rails reserve only the tab footprint and otherwise overlay the map.
