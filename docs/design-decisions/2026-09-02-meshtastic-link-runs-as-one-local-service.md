# Meshtastic Link runs as one local service

1. **Time and date:** 2026-09-02, America/New_York
2. **Name:** One local Link service owns the radio and Shared Picture
3. **Context:** Asset autonomy needs real-time access to the Shared Picture and the ability to request or publish data without blocking on a low-bandwidth radio. Embedding radio ownership in every local program would create competing connections, duplicate state, and language-specific integrations.
4. **Decision:** Each participating machine runs one Meshtastic Link service. It exclusively owns the radio and Shared Picture and serves multiple Link clients through a loopback-only JSON interface. The service gives every picture snapshot an atomic service session and revision. Its live event stream resumes after that revision without losing intervening changes, or rejects an expired or prior-session cursor and requires a new snapshot. The picture is read-only. Publishing state, reporting Task progress, requesting data, and managing subscriptions use explicit operations. Requests return an ID and complete asynchronously. Requests requiring an unavailable Gateway fail promptly rather than remaining queued. Raw packets and transport internals stay behind a diagnostic interface.
5. **Alternatives considered:** A library embedded separately in each Asset process was rejected because it permits competing radio owners and separate pictures. A file such as `world_state.json` was rejected because polling and whole-file replacement are poor real-time interfaces. Giving clients raw packets was rejected because it leaks transport internals into Asset behavior. Blocking local calls until radio completion was rejected because radio latency must not stall autonomous software.
6. **Consequences:** The Link service becomes a deployable process with a local lifecycle and interface contract. Local clients may use different programming languages without duplicating radio behavior. The service must aggregate local subscription demand, preserve request correlation, expose freshness, retain a bounded picture-event handoff buffer, and recover cleanly from client disconnects. The initial implementation should prefer ordinary loopback HTTP and server-sent events unless a measured requirement demands a different local transport.
7. **Location:** `docs/atlas-meshtastic-link/service-interface.md`, `CONTEXT.md`, and the future Meshtastic Link service package
