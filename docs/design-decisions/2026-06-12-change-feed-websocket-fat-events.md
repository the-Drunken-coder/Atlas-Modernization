# Design Decision

1. **Time & Date:** 2026-06-12 America/New_York
2. **Name:** Websocket change feed with fat events, post-commit emission, and burned-version gap skipping
3. **Context:** Atlas clients (web UI, asset services, SDK) previously learned about writes by polling, with a hard-refresh feel. Push is not just a cosmetic improvement: Atlas needs a live operator UI for asset, task, and object metadata changes while work is happening, and using few-second `changed-since` polling to approximate that live view would create materially more API traffic as long-running UI and SDK clients are added. A push channel was planned inside the Atlas SDK plan, then split into its own deliverable so it could be built before the SDK. Global write versions come from one PostgreSQL sequence serialized by the advisory write lock (`2026-06-10-global-write-version-lock.md`), and `GET /queries/changed-since` already provides cursor-based recovery with tombstones.
4. **Decision:** Serve a websocket at `/feed` from Atlas Core's own process. Events are fat — full serialized resource plus event type, resource type, ID, and global version — one event per frame, with tombstones for deletes and object metadata only (never content). Core's write paths hand committed changes (with before-and-after state) to an in-process hub via post-commit hooks; the hub buffers out-of-order arrivals and delivers in strict version order. Because PostgreSQL sequence values are not transactional, a failed write can burn a version that will never produce an event. Resource writes use a savepoint inside the existing globally locked transaction so a rejected statement can roll back while Core still reads the exact sequence range it consumed; only after the outer transaction rolls back are those versions reported to the hub as known-missing and skipped immediately. The short missing-version timeout remains the fallback for gaps Core cannot prove missing. Clients treat any version gap as a `changed-since` recovery trigger, so both skip paths are safe by contract. Subscriptions are four server-side filters (`all`, by ID, by type, tasks-for-entity with before-or-after reassignment routing), changeable over a live connection, starting empty. Auth is first-message (browsers cannot set websocket headers); the server then sends a `hello` frame carrying the protocol revision stamp. Slow consumers are disconnected when a bounded send buffer fills. Wire shapes are authored in Atlas Protocol JSON Schema, generated into TypeScript and Go validators, and structurally checked against the authored Go API.
5. **Alternatives considered:** Poll-only `changed-since` was rejected as the primary UI path because a long interval makes operator views feel stale and a short interval creates avoidable API traffic. Webhooks were rejected because Core calling back registered URLs does not work for browser UIs or assets behind flaky links. Thin "something changed" notifications were rejected because they force follow-up GETs and reintroduce ordering races. Postgres LISTEN/NOTIFY and internally tailing `changed-since` were rejected as emission mechanisms because neither carries the before-state the task-routing rule needs (and tailing adds a polling latency floor). A dedicated feed service was deferred until fanout, deployment, or isolation pain is real. Waiting indefinitely on missing versions was rejected after review found it froze the feed permanently on any burned version — e.g. an ordinary duplicate-create 409. Merely lowering the timeout was rejected because it would narrow the ordering window for delayed post-commit events without proving a version is missing. Per-error preflight queries were rejected because they duplicate database constraints and cannot cover every rejected statement that allocates a version.
6. **Consequences:** Real-time push exists with polling (`changed-since`) as the recovery and fallback path, so feed delivery can be best-effort-ordered rather than guaranteed-complete. Clients must implement the consumption contract (version-guarded application, gap-triggered recovery, reconnect catch-up) to get correctness. The feed is justified by live operator latency and traffic reduction; if those requirements disappear, poll-only `changed-since` is the simpler valid design. The feed shares Core's process and lifecycle; moving it out later means revisiting emission (post-commit hooks are in-process by nature). Routine rejected writes no longer impose the gap timeout, while unprovable missing versions still trade a brief delay for liveness. The simulation harness and a Postgres-backed end-to-end test (including consecutive rejected writes followed by successful events) guard the ordering and skip behavior.
