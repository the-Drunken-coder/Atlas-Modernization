# Design Decision

1. **Time & Date:** 2026-06-12 America/New_York (updated 2026-08-19)
2. **Name:** Websocket change feed with fat events and a transactional durable event log
3. **Context:** Atlas needs a live operator UI for asset, task, and object metadata changes without few-second polling. The original implementation assigned versions from a PostgreSQL sequence, published through in-process post-commit hooks, buffered arrivals in the hub, and maintained separate resource/tombstone recovery streams. Rejected transactions could burn sequence values, so additional skip and timeout mechanisms were required to keep delivery moving. Those compensations made two distinct sources of truth and multiplied recovery states.
4. **Decision:** Serve a websocket at `/feed` from Atlas Core's process. Events contain the event type, resource type, ID, global version, and the full serialized resource for creates and updates. Delete events omit the resource, and object content is never pushed. Every resource write locks and increments `atlas_change_clock`, writes the resource mutation, and appends the validated event to `atlas_change_events` in the same transaction. Task events also record their immutable Asset ID for `tasks_for_asset` routing. PostgreSQL `NOTIFY` only wakes the dispatcher, which tails committed rows in order and sends them through the subscription hub. `GET /queries/changed-since` reads the same log with one global cursor. Supported subscriptions are `all`, by ID, by type, and `tasks_for_asset`.
5. **Alternatives considered:** Poll-only changed-since remains too stale or too chatty for the operator UI. Webhooks do not fit browser clients or assets behind flaky links. Thin notifications force follow-up reads and ordering races. Keeping the sequence/post-commit design was rejected because its skip, timeout, out-of-order buffer, tombstone table, and six recovery cursors existed only to compensate for a non-transactional source. LISTEN/NOTIFY payloads are not durable enough to be authoritative, so notifications wake a database tail instead.
6. **Consequences:** Committed versions are contiguous, rejected writes do not advance the clock, websocket delivery and recovery use identical event envelopes, and restart recovery is a database read rather than in-memory gap bookkeeping. Clients still use version guards, gap-triggered recovery, and reconnect catch-up because connections can drop. The durable log grows with resource mutations and must be included in database backup/restore. The feed remains in Core's process; a future separate service can tail the same log without changing write paths.
7. **Location:** `packages/protocol/schema/jsonschema/atlas.schema.json`, `services/core/internal/feed/`, `services/core/internal/actions/change_hook.go`, `services/core/internal/actions/write_version.go`, `services/core/internal/database/migrations.go`, `services/core/internal/api/handlers/handler_feed.go`, `services/core/internal/api/handlers/handler_feed_integration_test.go`, `packages/sdk/src/sync-engine-recovery.ts`, `docs/atlas-change-feed/README.md`
8. **Notes:** Full design detail and the consumption contract live in `docs/atlas-change-feed/README.md`. Migration v4 replaces the earlier sequence/tombstone schema; the previous global-write-lock decision is historical context rather than the current mechanism.
