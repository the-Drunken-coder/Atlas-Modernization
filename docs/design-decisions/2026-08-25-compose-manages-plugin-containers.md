# The deployment orchestrator manages Plugin containers

1. **Time & Date:** 2026-08-25 10:43 EDT
2. **Name:** Docker Compose or the deployment orchestrator starts one container per configured Plugin
3. **Context:** Plugins must fail without taking down Atlas Core, but Atlas should remain one deployed system. Core could manage Docker directly, a shared host could run every Plugin, or the existing deployment orchestrator could manage isolated Plugin containers.
4. **Decision:** The deployment orchestrator manages one trusted container per configured Plugin. The bundled Atlas stack uses Docker Compose. Deployment configuration gives Core the Plugin ID and private base URL, but Core never receives Docker socket access or manages container installation, upgrades, restart policy, resource limits, or shutdown. The first architecture does not treat container networking as a Plugin sandbox; using the Source Gateway for external access is an implementation requirement. The first architecture has no separate Plugin Definition and Plugin Instance concepts: one configured Plugin ID maps to one deployment-managed container whose Plugin may be `starting`, `available`, or `unavailable`.
5. **Alternatives considered:** Core-managed containers were rejected because Docker socket access would give Core broad host authority and add an orchestration system to the application. A shared Plugin host was rejected because one Plugin failure could affect every Plugin and language or dependency conflicts would accumulate in the host.
6. **Consequences:** Plugin images and configuration are part of deployment configuration. The first-party Atlas Core CLI now edits that configuration and restarts the Compose deployment for catalog entries declared `query_only`; this operational addition is specified by `2026-08-30-first-party-plugin-catalog-and-map-area-interactions.md`. Core still has no installation API. Core rejects deletion of a Plugin-owned Tool Asset while its Plugin remains configured. Removing that configuration is the only uninstall path, after which the Tool Asset may be deleted once its Tasks are terminal. Container failure does not terminate Core. A Plugin manages its own concurrent requests and monitored areas instead of Atlas scaling multiple instances. Development scratch data may be cleared under the existing destructive development workflow, while production restart remains durable. Untrusted third-party images would require enforced egress isolation. They, horizontal Plugin scaling, arbitrary Plugin installation, taskable-Plugin lifecycle management, and a Plugin marketplace remain outside the first version.
7. **Location:** `docs/atlas-plugins/`, future Docker Compose Plugin configuration
