# First-party Plugin catalog and fixed map-area interactions

1. **Time & Date:** 2026-08-30 23:55 EDT
2. **Name:** Atlas Core CLI manages a first-party query-only Plugin catalog and the Command Interface renders fixed interaction metadata
3. **Context:** Plugin v1 deliberately deferred install management and declarative browser integration until a real Plugin established the shared contract. Building Scan needs an operator to enable one trusted container, select a bounded rectangle, invoke a query-only Operation, and inspect spatial results without adding provider-specific deployment or UI code to shared systems.
4. **Decision:** Each Plugin is a self-contained `plugins/<plugin_id>/` folder with `atlas-plugin.json`, source, tests, Dockerfile, Compose overlay, Core endpoint fragment, and Source Gateway connector fragment. Root tooling discovers these folders, verifies their convention, builds them, rejects Plugin-owned terms or imports in shared production code, and generates the Atlas Core CLI catalog. Atlas Core releases publish catalog Plugins as multi-architecture GHCR images and record exact digests and deployment assets in the matching CLI package. The CLI enables and disables only catalog entries declared `query_only`, using staged private fragments, complete Compose validation, restart-based service changes, health waits, and rollback. Core and Source Gateway load sorted strict fragment directories and fail startup on invalid, duplicate, or partial configuration. Protocol Operation descriptors may advertise the fixed, non-executable `{ "kind": "map_area" }` interaction. The shared `MapArea`, Polygon or MultiPolygon result, provenance, attribution, retrieval time, and truncation contracts are validated by the runtime and SDK. Core validates the descriptor but treats Operation bodies as opaque JSON. The Command Interface discovers this interaction through `GET /plugins` and provides one generic left-panel runner, rectangle editor, map overlay, and results inspector without branching on Plugin IDs, Operation IDs, or providers.
5. **Alternatives considered:** Plugin-specific Core settings and browser components were rejected because every new Plugin would spread dedicated code into shared systems. Executable Plugin UI was rejected because trusted code execution, compatibility, styling, and browser security are unnecessary for a fixed rectangle interaction. Arbitrary image or bundle installation was rejected because it would require a marketplace trust, compatibility, credential, and lifecycle model. Hot reload was rejected because manifests are process-cached and restart-based changes are simpler and observable. A generic schema-driven form system was rejected because the concrete forcing case needs only one spatial interaction.
6. **Consequences:** Another query-only spatial Plugin adds one Plugin folder and release metadata; shared production code does not change. Removing a Plugin folder and regenerating catalog artifacts removes its shared deployment presence. Building Scan is disabled by default and acts as both a useful feature and the deletion test for this boundary. The CLI package and deployed Core version must match for Plugin mutations, while status and logs remain read-only across CLI-only drift. Taskable Plugin removal remains deferred because active Tasks need draining and terminalization rules. This decision does not create arbitrary UI extensions, third-party installation, hot upgrades, or a marketplace. Additional interaction kinds require their own fixed Protocol contracts and generic renderer.
7. **Location:** `plugins/`, `scripts/plugins.mjs`, `packages/protocol/`, `packages/plugin-runtime/`, `packages/sdk/`, `services/core/`, `surfaces/core-cli/`, `surfaces/command-interface/`
