# Plugins release independently from Atlas Core

1. **Time & Date:** 2026-09-01 12:40 EDT
2. **Name:** First-party Plugins have independent releases managed by the host-side Atlas Core CLI
3. **Context:** Plugin v1 runs each Plugin in its own container, but the Atlas Core release workflow builds every catalog Plugin and copies its image digest and deployment files into the matching CLI package. Updating one Plugin therefore requires a new Core package even when the Core runtime contract has not changed. Atlas needs independent Plugin delivery while Core and the Command Interface continue to provide the fixed routes, Atlas actions, Source Gateway access, and declarative interactions that Plugins use.
4. **Decision:** Each trusted first-party Plugin has its own immutable Semantic Version and release workflow. One Plugin release consists of a strict UTF-8 JSON `.atlas-plugin` document and the immutable multi-architecture image that document pins by digest. The document is declarative and cannot run installation hooks or provide arbitrary Compose configuration. One Atlas catalog publishes a stable channel through GitHub Pages, while release documents remain GitHub Release assets and images remain GHCR artifacts. A protected release workflow signs each catalog with Ed25519 and republishes it weekly so expiry stays bounded even without a Plugin release. The CLI trusts embedded public keys and verifies the signed catalog, which pins each release document hash and thereby its image digest. The host-side `atlas-core` terminal menu installs, updates, enables, disables, rolls back, and uninstalls Plugins without granting Docker or host-filesystem authority to the Core server or Command Interface. A catalog entry, an Installed Plugin, an Enabled Plugin, and runtime health are separate. The manager retains the selected release and one previous release, restores failed updates, and accepts only explicit operator-approved updates or rollbacks to compatible non-revoked releases. Operator configuration remains separate from releases and survives update, disable, and uninstall until an explicit purge. Compatibility follows exact supported majors of the Plugin package, Core-to-Plugin, and Plugin-to-Source-Gateway contracts plus supported fixed Command Interface interactions, not Atlas Core SemVer alone. The CLI checks before deployment, and runtime peers repeat and enforce their protocol majors. Plugin management requires the matching Docker engine but may operate across CLI and Core package-version drift. Management may restart the existing deployment but does not change the Core version. The first managed scope is trusted query-only Plugins in this repository. Plugins cannot depend on other Plugins.
5. **Alternatives considered:** Publishing Plugins only with Core was rejected because it forces unrelated releases and prevents individual updates. Encoding installation metadata only inside the runtime image was rejected because the manager needs reviewable metadata before starting Plugin code. Package-supplied Compose and executable hooks were rejected because they grant unnecessary host authority. Core-server or browser installation was rejected because it would require a privileged deployment process. Arbitrary catalogs and images, unattended updates, hot upgrades, taskable-Plugin lifecycle management, and mandatory separate repositories were rejected from the first managed release because each adds a separate trust, lifecycle, or coordination problem.
6. **Consequences:** The Core release workflow will stop building Plugin images and embedding Plugin catalogs or deployment assets. Each Plugin workflow publishes and verifies its image and release document before an immutable version enters a newly signed catalog. The CLI needs independent Installed Plugin state, compatibility checks, generated deployment configuration, explicit update and rollback actions, health verification, revocation warnings, configuration retention and purge, and interrupted-transaction recovery. The signed catalog, rather than a second bundle signature, authenticates release bytes and image digests. A Plugin update may restart Core or Source Gateway because manifests and connector configuration remain restart-based. Third-party trust, taskable Plugin draining and Tool Asset handling, prerelease channels, Plugin dependencies, unattended updates, and hot replacement remain deferred.
7. **Location:** `docs/atlas-plugins/`, `CONTEXT.md`, `plugins/`, `scripts/plugins.mjs`, `surfaces/core-cli/`, `.github/workflows/`, `services/core/`, `packages/plugin-runtime/`, `packages/protocol/`, `packages/sdk/`, `surfaces/command-interface/`
8. **Notes:** This decision supersedes the Core-packaged catalog and matching-release portions of `2026-08-30-first-party-plugin-catalog-and-map-area-interactions.md` and the versionless compatibility portion of `2026-08-25-core-connects-to-configured-plugins-over-http.md`. Their fixed runtime routes, deployment ownership, and generic `map_area` interaction decisions remain in force.
