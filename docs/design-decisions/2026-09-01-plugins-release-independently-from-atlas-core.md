# Plugins release independently from Atlas Core

1. **Time & Date:** 2026-09-01 12:40 EDT
2. **Name:** First-party Plugins have independent releases managed by the host-side Atlas Core CLI
3. **Context:** Plugin v1 runs each Plugin in its own container, but the Atlas Core release workflow builds every catalog Plugin and copies its image digest and deployment files into the matching CLI package. Updating one Plugin therefore requires a new Core package even when the Core runtime contract has not changed. Atlas needs independent Plugin delivery while Core and the Command Interface continue to provide the fixed routes, Atlas actions, Source Gateway access, and declarative interactions that Plugins use.
4. **Decision:** Each trusted first-party Plugin has its own immutable Semantic Version and release workflow. One Plugin release consists of a strict UTF-8 JSON `.atlas-plugin` document and the immutable multi-architecture image that document pins by digest. The document is declarative and cannot run installation hooks or provide arbitrary Compose configuration. One Atlas catalog publishes a stable channel through GitHub Pages, while release documents remain GitHub Release assets and images remain GHCR artifacts. A protected append-only ledger, ordered Ed25519 key epochs with per-epoch sequence floors, bounded catalog inputs, rejected duplicate release identities, and atomic local receipts provide catalog integrity and rollback protection. A dedicated scheduled workflow republishes the catalog weekly so expiry stays bounded without depending on the manually approved Core release environment. The host-side `atlas-core` terminal menu installs, updates, enables, disables, rolls back, and uninstalls Plugins without granting Docker or host-filesystem authority to the Core server or Command Interface. A catalog entry, an Installed Plugin, an Enabled Plugin, and runtime health are separate. The manager retains the selected release and one previous release, restores failed Plugin updates, and accepts only explicit operator-approved updates or rollbacks to compatible non-revoked releases. An approved update may replace a revoked selection with the greatest permitted release even when its version is lower. Package schema 1 has no general Plugin setting or secret lifecycle. The manager supplies the fixed Source Gateway origin and, for SDK-using Plugins, the fixed Core origin plus one shared deployment-owned managed API key that it rotates through a crash-recoverable transaction. Compatibility follows the package schema, membership in the deployed private-protocol supported-major sets, the exact Atlas Protocol revision when a Plugin uses the SDK, and coordinated fixed Command Interface interactions, not Atlas Core SemVer alone. Restart-capable Plugin operations use the installed Core's complete retained deployment bundle and exact image, so CLI/Core package drift cannot replace Core. The manager regenerates disposable Plugin deployment files from retained inputs before every start. Explicit repair starts may restore only the recorded Core package bundle and exact image digests without selecting a new release. Durable root-level transactions hold complete before-state bytes and reclaim only locks whose owner is provably dead. A failed Core update never restarts the prior image against migrated or uncertain storage. The first managed scope is trusted query-only Plugins in this repository. Plugins cannot depend on other Plugins.
5. **Alternatives considered:** Publishing Plugins only with Core was rejected because it forces unrelated releases and prevents individual updates. Encoding installation metadata only inside the runtime image was rejected because the manager needs reviewable metadata before starting Plugin code. Package-supplied Compose and executable hooks were rejected because they grant unnecessary host authority. Core-server or browser installation was rejected because it would require a privileged deployment process. Arbitrary catalogs and images, unattended updates, hot upgrades, taskable-Plugin lifecycle management, and mandatory separate repositories were rejected from the first managed release because each adds a separate trust, lifecycle, or coordination problem.
6. **Consequences:** The Core release workflow will stop building Plugin images and embedding Plugin catalogs or deployment assets. Each Plugin workflow publishes and verifies its image and release document before an immutable version enters the signed catalog ledger. The CLI needs independent Installed Plugin state, a complete hashed Core deployment bundle, compatibility checks, generated deployment configuration, fixed Core and Source Gateway connection injection, recoverable shared-key rotation, exact running-image checks, explicit update and rollback actions, health verification, revocation warnings, duplicate-identity rejection, atomic catalog receipts, exact-package bundle repair, exact-digest image repair, and crash-safe transaction recovery. Core updates must load enabled Plugins from local signed records, preflight them against the target Core, and commit Core state only after all enabled Plugins pass image, manifest, and health checks. Once a target Core starts, failure recovery must inspect migration state and either restore the paired pre-deploy backup or fix forward before it can complete. The signed catalog, rather than a second bundle signature, authenticates release bytes and image digests. A Plugin update may restart Core or Source Gateway because manifests and connector configuration remain restart-based, but it cannot change the Core image. Revocation remediation may intentionally downgrade a Plugin to the greatest permitted release. General Plugin configuration remains deferred until a concrete Plugin requires it. The first independent Core update refuses to proceed while a bundled-v1 Plugin remains enabled; operators disable and reinstall those Plugins instead of receiving an inferred signed receipt. Third-party trust, taskable Plugin draining and Tool Asset handling, prerelease channels, Plugin dependencies, unattended updates, and hot replacement remain deferred.
