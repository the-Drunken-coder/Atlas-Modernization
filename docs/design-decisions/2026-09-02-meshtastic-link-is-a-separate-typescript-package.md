# Meshtastic Link is a separate TypeScript package

1. **Time and date:** 2026-09-02, America/New_York
2. **Name:** Build one Meshtastic Link service package with Asset and Gateway modes
3. **Context:** Atlas already has a MeshCore-specific FieldLink package, a TypeScript workspace, a separate Atlas Protocol source of truth, reserved Asset and Gateway application boundaries, and whole-system simulations. Meshtastic Link needs production transport code, generated contracts, a local service and CLI, radio configuration, and a no-cheating simulator without coupling those responsibilities to MeshCore or Atlas Core.
4. **Decision:** Create `packages/meshtastic-link` as a TypeScript and Node 24 npm workspace. One Link service implementation and executable supports explicit `asset` and `gateway` modes using one static Radio profile and shared transport behavior. Asset mode joins through the Gateway. Gateway mode loads durable Link membership and admits Assets without joining through itself. Atlas Core access remains in the Gateway application. The Radio contract generator and checked-in output live in this package and consume Atlas Protocol as their source. Reusable packet simulation lives in the package; whole-Atlas scenarios remain in `simulations`. The first hardware adapter uses USB serial behind an Atlas-owned interface. Local overload is explicit: a confirmed operation is rejected before acceptance if bounded tracking resources cannot be reserved.
5. **Alternatives considered:** Adding Meshtastic to FieldLink was rejected because FieldLink owns MeshCore-specific behavior. Separate Asset and Gateway Link service implementations were rejected because their radio mechanics and profile must remain identical. Putting generated Radio code in Atlas Protocol was rejected because Protocol must not depend on one communication method. Building the production Link service in Python was rejected because the repository's application packages, generated SDK work, and deterministic simulator are TypeScript, while an official Node serial client is available behind an adapter. Implementing Bluetooth and Wi-Fi radio connections initially was rejected because USB serial serves the first Heltec V3 companion-computer deployment.
6. **Consequences:** The root workspace and build scripts will eventually add one package. Meshtastic client-library churn is isolated to one adapter. The simulator can use the same production Link service seams without importing Core. Asset and Gateway integration happens later through their reserved application boundaries. The first milestone proves one generated position message end to end in simulation before physical-radio or encoding optimization work.
7. **Location:** Future `packages/meshtastic-link`, `simulations`, `edge/asset`, `edge/gateway`, and `docs/atlas-meshtastic-link/implementation-sequence.md`
