# Core storage recovery testing

The storage recovery tier runs Atlas Core's existing upload-intent, deletion-outbox, and object-deletion-fence assertions against disposable PostgreSQL and MinIO containers. It adds real-storage cases for a process crash after MinIO accepts a blob, a failed deletion followed by recovery, a queued path that became live, and an upload to unavailable storage.

Run the required tier from the repository root:

```bash
services/core/scripts/run_storage_recovery_tests.sh
```

Run the nightly tier with three shuffled repetitions and three consecutive injected deletion failures per repetition:

```bash
services/core/scripts/run_storage_recovery_tests.sh --nightly
```

Both commands require Docker, Git, Go, and Python 3. Missing commands, an unavailable Docker daemon, image pull or readiness failures, skipped live dependencies, malformed coverage, a missing selected test, or owned-container cleanup failure makes the command fail. The runner does not retry failures.

## Isolation and cleanup

Each invocation starts PostgreSQL 15 and MinIO with unique container names, random loopback ports, no host bind mounts, and no named volumes. The tests ignore ordinary `DATABASE_URL` and `MINIO_*` settings for storage setup. The runner supplies dedicated `ATLAS_STORAGE_RECOVERY_*` values, and the test helper rejects a non-loopback storage endpoint.

The runner initializes the job-exclusive `public` schema through the existing Core schema path for retained tests that predate per-test schemas. Every new recovery case owns a UUID PostgreSQL schema and UUID MinIO bucket. The older storage tests run serially in the job-exclusive PostgreSQL container and clean their rows. Object IDs are `sr-` plus a UUID and remain within the Protocol's 50-character limit. MinIO paths are generated by the production storage client, queried from persisted state when needed, and treated as opaque values.

Go cleanup empties each test bucket. The runner's exit trap captures dependency logs and inspection output before removing both exact owned containers, including after a test or evidence-capture failure. A cleanup failure changes an otherwise successful result to failure and identifies the affected container in the artifacts.

## Behavior covered

| Case | Observable assertions |
| --- | --- |
| Interrupted upload | A child test process exits immediately after the production client stores bytes in MinIO. The upload intent remains durable, a new upload has no completed metadata, and a replacement continues to reference and serve its previous bytes. Recovery honors the lease and orphan grace, deletes only the interrupted path, and leaves a permanent path fence. |
| Deletion outage | A test-side fault blocks the first required deletion attempt while the underlying blob remains in real MinIO. Retry state advances and schedules a later attempt. After the fault is removed, reconciliation deletes the blob and retains the permanent path fence. Nightly mode repeats the fault three times to cover successive retry state. |
| Live path protection | Real bytes and valid object metadata share the queued bucket and path. Reconciliation removes the mistaken queue entry and preserves the exact bytes. |
| Unavailable upload storage | Uploading to a missing isolated bucket returns an error, creates no Object metadata, clears the upload intent, and records durable cleanup. After the bucket becomes available, reconciliation completes that cleanup and fences the path. |
| Existing recovery contracts | The selected suite retains upload lease renewal and loss, orphan grace, advisory lock ordering, live-path checks, replacement and deletion races, retry backoff, committed deletion ordering, persisted-bucket routing, and permanent deletion fencing. |

The injected deletion error is test support around the production storage interface. The stored object before and after that error is read from real MinIO through the production client. The crash child uses the same isolated database schema and MinIO bucket as its parent. No deployed service, retained database, retained bucket, production confirmation, or safety check is bypassed.

## Coverage evidence

`storage.coverage.out` measures the Go `internal/actions` test binary with `internal/actions`, `internal/database`, `internal/storage`, and `internal/testenv` instrumented. Those tests invoke the real production PostgreSQL and MinIO clients in process. There is no separately running Atlas Core server, so the profile is not server-process or public HTTP coverage. The deliberately terminated child test process is also outside this profile. Its exit code, durable database intent, real stored bytes, and later parent-process reconciliation are behavior evidence rather than coverage evidence.

The coverage checker reports exact statement ratios for the whole profile and each instrumented module. Its floors are based on the required command and retain a small margin for branches that depend on scheduling. Coverage percentage supports the behavior assertions; it does not replace them.

## Artifacts and failure classification

Each run writes a unique directory under `.atlas/core-storage-recovery/` containing:

- `metadata.txt` with the exact Git revision, tool versions, mode, image digests, selector, repetitions, coverage ownership, and readiness evidence
- `commands.log` with the executed commands while omitting disposable passwords
- dependency pull, startup, runtime, inspection, and cleanup logs
- `coverage-checker-tests.log`, `selection-verifier-tests.log`, `schema-initialization.log`, `storage.log`, `selection-verification.log`, `storage.coverage.out`, and `coverage.txt`
- `classification.md`, which records a clean run or leaves the first failed command unclassified for assessment

For an initial failure in a new storage behavior assertion, stop that case without changing its expectation or retrying. Report the clean revision, exact command, dependency setup, expected and observed behavior, artifact directory, and first error for manual assessment. Record corrected setup failures, verified product defects, and unavailable verification separately. A correct product failure remains active for a later product repair.

The required workflow has a 25-minute bound, including the worst-case bounded pulls, schema initialization, test process, evidence capture, and cleanup. The nightly workflow has a 45-minute bound and expands failure attempts and ordering. GitHub Actions uploads the owned artifact directory even when the run fails.
