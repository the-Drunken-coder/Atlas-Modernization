# Problem Report

1. **Time & Date:** 2026-09-17T15:17:29Z
2. **Name:** Direct Plugin install and update do not own cancellation
3. **Issue:** The direct `atlas-core plugins update` command can receive a cancelled Plugin-operation outcome and still report success, while direct Plugin install and update have no CLI `SIGINT` bridge to `cancelPending()` and therefore cannot perform the safe-cancellation flow used by direct enable/disable.
4. **Severity:** S3 (Moderate)
5. **Location:** `surfaces/core-cli/src/application.ts:5487-5494,5555-5577,1560-1618,1732-1837`; `surfaces/core-cli/src/cli.ts:1-6`; cancellation contract in `surfaces/core-cli/src/operator.ts:152-155,191-208`
6. **Expected:** Every direct Plugin mutation that can be cancelled should install a temporary `SIGINT` handler, request `cancelPending()`, wait for the operation's rollback/recovery, restore cancellation state, print a cancellation message, and return a nonzero cancellation status. A cancelled `PluginOperationOutcome` must never be discarded as success.
7. **Actual:** `runCLI` wraps only `plugins enable` and `plugins disable` in `runDirectPluginMutation` (which installs the signal handler and maps `status: "cancelled"` to exit 130). It directly awaits `pluginInstall` and `pluginUpdate` and then unconditionally returns 0. `pluginUpdate` catches `CommandCancelledError` and returns `{ status: "cancelled" }` even when no activity reporter was supplied, so that outcome is ignored by the direct switch. `pluginInstall` instead rethrows cancellation when no reporter is supplied, which reaches the outer catch as exit 1 but still has no direct signal handler. The package entrypoint only awaits `runCLI` and assigns its result to `process.exitCode`; with no listener in that path, ordinary Ctrl-C terminates the Node process instead of initiating the deployment's safe cancellation flow.
8. **Reproduction:**
   1. At `43b5928ceba19bc95d00d578cc6ed9c03319167e`, invoke `runCLI(["plugins", "update", pluginId], context)` for an initialized deployment. The direct switch calls `deployment.pluginUpdate(command.pluginId)` without a reporter or signal wrapper (`application.ts:5487-5490`) and then returns 0 (`application.ts:5505`).
   2. Cause the operation's `CommandRunner` to be cancelled programmatically while its update-resolution fetch or Compose command is pending. `CancellableCommandRunner` converts a cancelled command result into `CommandCancelledError` (`application.ts:686-690`); `pluginUpdate` catches that error and resolves with `status: "cancelled"` (`application.ts:1818-1834`). The direct caller ignores that value and returns 0, with no `[cancel]` output and no `resumeAfterCancellation()` call.
   3. For a real user interruption, run `atlas-core plugins install ...` or `atlas-core plugins update ...` and press Ctrl-C during the mutation. Unlike the tested enable/disable path (`application.ts:5555-5577`, `application.test.ts:5234-5254,5392-5411`), neither direct operation has a `process.on("SIGINT", ...)` registration. `cli.ts` has no signal registration, so the normal Node signal action terminates the process rather than requesting `deployment.cancelPending()`.
9. **Notes:** This is scoped to direct commands. The TUI already passes an activity reporter through `runPluginActivity` and handles cancelled outcomes (`surfaces/core-cli/src/terminal-ui.tsx:446-544`), and the application tests exercise programmatic Plugin-update cancellation through `operator.cancelPending()` (`application.test.ts:6904-6948,7146-7190`). Those tests establish that cancelled update outcomes are reachable and intentional; they do not cover the direct `runCLI(["plugins", "update", ...])` path. The install distinction is material: its no-reporter branch rethrows (`application.ts:1602-1607`), so the report does not claim that install currently exits 0 on a returned cancellation. A focused regression test should exercise direct install/update with a cancelled command and assert cancellation handling, signal-listener cleanup, and a nonzero status; ordinary Ctrl-C should be tested in a child process because the current behavior is process termination, not a Promise result.
