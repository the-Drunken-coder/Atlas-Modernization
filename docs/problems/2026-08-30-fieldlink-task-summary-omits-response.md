1. **Time & Date:** 2026-08-30T15:03:20Z
2. **Name:** FieldLink Task exercise summary omits application response
3. **Issue:** A successful Task exercise receives an application status and body, but the final machine-readable summary does not project either value even though the FieldLink evidence contract promises the Task application status. The TUI's summary section consequently cannot show the Task result.
4. **Severity:** S4 (Minor)
5. **Location:** `packages/fieldlink/src/cli.ts` (final summary assembly at lines 331-385), `packages/fieldlink/src/messages/task.ts`, `packages/fieldlink/README.md` (evidence contract at lines 288-299), and `packages/fieldlink/tools/fieldlink_tui.py` (`summary_lines` at lines 389-430)
6. **Expected:** After a correlated Task response, `summary.json` should preserve the response's application status and body, and the TUI's final summary should present those values or a typed Task response field. A summary-only consumer should not need to parse the raw event stream to recover the result.
7. **Actual:** `waitForExerciseCompletion` returns transport-only `ExerciseResponseEvidence`; the received Task message remains outside that evidence object. The CLI summary stores that transport data as `response` and adds `verification.atlasStatus`, `resourceResponse`, or `runtimeResponse` only for Resource and Runtime messages. A Task response therefore yields only `verification: { correlation: "matched" }`; its `status` and `body` are absent from `summary.json`. `summary_lines` renders `atlasStatus` only when present, so the Task result section omits the application outcome. The raw `message` event still contains the complete Task response and the TUI transcript can display it, providing a workaround but not repairing the summary contract.
8. **Reproduction:**
   1. Run a Node 24 mocked CLI harness that imports `main`, replaces `AdapterProcessNode.start` with two in-memory adapter nodes, and replaces `TestArtifacts.create` with a sink that captures the final summary. Return matching radio metadata and make the mocked A send a valid Task request to B; make B's test responder send back `{ type: "task", kind: "response", request_id, status: 201, body: { task_id: "task-1", status: "started" } }`.
   2. Invoke `main(["test", "--a", "/dev/cu.a", "--b", "/dev/cu.b", "--message", "task", "--channel", "1", "--timeout-ms", "1000", "--allow-inbox-drain"])`.
   3. Observe exit code `0` and a captured summary with `status: "passed"`, transport metrics under `response`, and `verification: { correlation: "matched" }`, but no `verification.atlasStatus`, `taskResponse`, or `status`/`body` for the received Task message. The focused probe produced `hasAtlasStatus: false` and `hasTaskResponse: false` while the mocked response had status `201` and a non-empty body.
   4. Feed the equivalent summary to `fieldlink_tui.summary_lines`; it renders correlation and transport statistics but no Atlas status or Task body. Feed the raw `message` event to `RunView.observe` and the response is still recoverable there, confirming that the omission is in final-summary projection rather than Task decoding or correlation.
9. **Notes:** `packages/fieldlink/README.md:290-299` explicitly says verification reports the application status carried by a Resource, Runtime, or Task response. The smallest repair is to project the received application message generically (or add a typed `taskResponse`) alongside the existing Resource and Runtime fields, then add a mocked CLI summary regression and a TUI assertion for Task status/body. No hardware or external service was used.
