1. **Time & Date:** 2026-08-30T14:55:13Z
2. **Name:** Persisted object bucket is ignored by storage operations
3. **Issue:** Object uploads persist the storage bucket in the JSON metadata, but download, delete, replacement cleanup, and queued deletion retries use only the storage client's bucket configured for the current Core process. Restarting the same Core database with a different `MINIO_BUCKET` therefore disconnects existing metadata from its blob.
4. **Severity:** S3 (Moderate)
5. **Location:** Atlas Core object actions and storage client, `services/core/internal/actions/object_actions.go`, `services/core/internal/actions/object_upload.go`, `services/core/internal/actions/object_storage_deletions.go`, and `services/core/internal/storage/storage.go`
6. **Expected:** Every operation on an uploaded object uses the bucket persisted with that object. Downloads should read `objects.path` from `objects.json.bucket`; deletion and replacement cleanup should delete that same bucket. A queued deletion should retain and use its recorded bucket even if the process configuration changes.
7. **Actual:** `ObjectActions.Delete` records `a.storage.Bucket()` in the deletion outbox and calls `DeleteObjectPath` without a bucket argument (`object_actions.go:317-346`). `ObjectActions.Download` passes only the path to `StreamObjectPath`, and the storage client always calls MinIO with `c.bucket` (`object_actions.go:370-378`, `storage.go:206-235`). Upload replacement captures the current bucket, writes the new metadata with it, and queues/deletes the previous path in that current bucket without consulting the previous object's JSON bucket (`object_upload.go:224-225`, `299-316`, `340-343`). Reconciliation skips an outbox row whose recorded bucket differs from the current bucket and has no alternate client/path to process it (`object_storage_deletions.go:288-318`). The object guide explicitly says downloads use the stored path and bucket (`services/core/docs/database-structure/objects.md:61-64`).
8. **Reproduction:**
   1. Start a durable Core database with storage bucket `atlas-old`, upload `object-1`, and retain its path. Confirm the object JSON has `"bucket":"atlas-old"` and the blob exists at `atlas-old/<path>`.
   2. Stop Core and restart it against the same database with `MINIO_BUCKET=atlas-new`; provision `atlas-new` so durable startup succeeds.
   3. Request `GET /objects/object-1/download`. The action reads the stored path but the storage client requests `atlas-new/<path>`, so the old blob is reported missing. If the same key exists in `atlas-new`, the response reads the wrong blob instead.
   4. Delete `object-1`. The transaction queues `(atlas-new, <path>)` and immediate cleanup targets `atlas-new`; a missing key can be treated as a successful idempotent delete, leaving `atlas-old/<path>` orphaned. An outbox row created before the restart for `(atlas-old, <path>)` is repeatedly deferred by the configured-bucket mismatch.
   5. Alternatively, upload a replacement for an existing object after the restart. The replacement is written to `atlas-new`, while cleanup of the previous path also targets `atlas-new`; the old blob in `atlas-old` remains orphaned.
9. **Notes:** This is a source-trace finding; no live MinIO or destructive deployment was run. The narrow existing action tests pass but use fakes with the single configured bucket and do not vary a persisted object bucket. The storage abstraction has no bucket parameter on `StreamObjectPath` or `DeleteObjectPath`, so the smallest durable fix is to make storage operations bucket-aware and carry the persisted bucket through object deletion, download, replacement cleanup, upload-failure cleanup, and reconciliation. Add focused tests with distinct old/current buckets, including a same-path object in the current bucket and an old-bucket outbox row.
