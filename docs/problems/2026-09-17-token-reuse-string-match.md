# Problem Report

1. **Time & Date:** 2026-09-17T15:24:40Z
2. **Name:** Token-reuse recovery depends on Core's human-readable message
3. **Issue:** The command interface decides whether a 400 token-reuse response is proven reuse for the current Entity by matching a human-readable message substring. The current Core Entity action emits that wording, but the cross-package contract has no dedicated structured error code or metadata.
4. **Severity:** S5 (Note)
5. **Location:** `surfaces/command-interface/src/atlas/data-source.ts:182-249,399-405`; `services/core/internal/actions/entity_actions.go:168-229`; `services/core/internal/actions/resource_instance_token.go:47-59`; `packages/protocol/schema/jsonschema/atlas.schema.json:582-648`
6. **Expected:** Recovery classification should use a stable structured signal that distinguishes same-Entity token reuse from generic token reuse, with the contract represented in the protocol or an explicit shared contract test. Human-readable `message` text should remain explanatory rather than control flow input.
7. **Actual:** `isResourceInstanceTokenReuse` requires status 400, `VALIDATION_ERROR`, and the exact substring `resource instance token has already been used for this entity instance` (`data-source.ts:399-405`). The SDK preserves the payload's message but prefixes it with status and error code (`packages/sdk/src/http.ts:313-328`), so this substring is the UI's only discriminator. Core's token table returns only generic `VALIDATION_ERROR` text (`resource_instance_token.go:47-59`), and `entity_actions.go` changes only the message when the stored hash belongs to the requested Entity (`entity_actions.go:174-178,216-229`). The protocol ErrorCode enum contains `VALIDATION_ERROR` and `PRECONDITION_FAILED`, but no token-reuse-specific code or scope field (`atlas.schema.json:582-648`).
8. **Reproduction:**
   1. Start `createGeofeature`, which persists a pending token and retries with the same `Atlas-Resource-Instance-Token` after a lost POST response (`data-source.ts:182-219`).
   2. For the current same-Entity token, Core returns the longer message and the interface accepts the fresh Entity even when its alias or geometry changed (`data-source.ts:231-241`). The focused regression test exercises this at `surfaces/command-interface/src/atlas/data-source.test.ts:844-876`, and Core's integration test asserts the same wire message at `services/core/internal/integration/ifmatch_test.go:165-183`.
   3. Change only Core's message wording, punctuation, or localization while leaving the 400 status and `VALIDATION_ERROR` semantics unchanged. The classifier then returns false. Because the failed request is neither transport, 5xx, nor proven reuse, `createGeofeature` clears the pending token and throws at `data-source.ts:208-214` instead of attempting recovery. This is a silent cross-package maintenance regression, not a currently observed mismatch.
   4. The generic message remains intentionally conservative: the matching recreated Entity is recovered only through alias and geometry matching (`data-source.test.ts:878-914`), demonstrating that the two message variants carry different control-flow meaning.
9. **Notes:** Verdict is confirmed maintenance/contract fragility, not a current runtime defect. Static tracing confirms today's Entity/Core behavior and the existing focused tests encode the exact string on both sides. No dedicated token-reuse error code or metadata was found in the current protocol schema. No source changes were made. The focused TypeScript test was not run because this clean worktree has no installed `node_modules`; the report is based on exact current-source inspection and existing test cases. A stable error code such as same-Entity versus generic token reuse, plus a protocol/contract test, would make the behavior resilient to copy edits.
