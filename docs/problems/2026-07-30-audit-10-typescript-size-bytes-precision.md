# TypeScript can silently corrupt valid large size_bytes values

1. **Time & Date:** 2026-07-30T08:33:00Z
2. **Original Audit Finding:** 10
3. **Validation Status:** Confirmed against `main` at `2426bb6`.
4. **Name:** TypeScript can silently corrupt valid large `size_bytes` values
5. **Affected Surface & Severity:** Atlas Protocol TypeScript types/validators and Atlas SDK object create, update, read, and feed/query response paths; S3 (Moderate). This is silent metadata corruption at a valid but extreme wire-contract value.
6. **Current vs. Expected:** The schema permits every non-negative integer representable by Core's `int64` fields, while generated TypeScript represents `size_bytes` as `number` and validates only finiteness, integrality, and non-negativity. JSON parsing `9007199254740993` therefore produces `9007199254740992`; the generated validator accepts it, the SDK returns the rounded value inbound, and `JSON.stringify` transmits the rounded value outbound. Every protocol-valid `size_bytes` should round-trip exactly through supported JavaScript clients.
7. **Concrete Source Evidence:** `atlas_protocol/schema/jsonschema/atlas.schema.json:781-784`, `:846-849`, `:953-961`, `:1039-1047`, and `:1129-1132` have no maximum. Generated types use `number` at `atlas_protocol/generated/typescript/index.ts:196-218`, `:230-255`, and `:268-276`; generated validators use `Number.isInteger` but not `Number.isSafeInteger` at `index.ts:466-475` and `:494-495`. `atlas_sdk/src/http.ts:75-91` serializes request bodies with `JSON.stringify`. Core and generated Go use `*int64` (`atlas_core/internal/api/handlers/handler_requests.go:155-185`; `atlas_protocol/generated/go/atlasprotocol/types.go:154-175`), so the accepted cross-language ranges currently differ.
8. **Reproduction / Static Proof:** On Node 25.9.0, `JSON.parse('{"object_id":"o","size_bytes":9007199254740993}')` yielded `9007199254740992`; `isObjectCreateRequest` returned `true`; and `JSON.stringify` produced `{"object_id":"o","size_bytes":9007199254740992}`. A two-case temporary SDK Vitest probe confirmed `client.objects.create(...)` sent that rounded body and `client.objects.get(...)` returned the rounded value from an exact inbound JSON response. `vitest run atlas-large-size-bytes.test.ts --root /tmp --environment node` passed both corruption assertions.
9. **Root Cause:** JSON Schema's unconstrained `integer` range is wider than JavaScript's exact integer range, and generated validators use `Number.isInteger` rather than making the wire contract safe for every supported language.
10. **Simplest Correct Proposed Solution:** Add a wire-level maximum of `9007199254740991` (`Number.MAX_SAFE_INTEGER`) to every `size_bytes` schema occurrence, preferably through one focused reusable schema definition. Regenerate artifacts. Do not introduce decimal strings, `bigint`, or dual encodings: current object-size requirements do not need values above the safe range.
11. **Acceptance Criteria / Regression-Test Plan:** Protocol validation in Go and generated TypeScript must accept 0 and `9007199254740991` and reject `9007199254740992` and larger values for object create, update, blob, resource, and detail resource shapes. Add an SDK round-trip test at the maximum and retain generated-artifact checks.
12. **Scope / Non-Goals:** Do not globally cap unrelated protocol integers without separate evidence. Feed/change versions already have SDK-specific safe-integer checks and are not part of this note. This does not propose support for objects remotely near the new maximum size.
13. **Overlaps:** Finding 11 concerns the same generated TypeScript validator surface but a separate recursion failure. Finding 8 concerns Core request/schema acceptance, not numeric representation.
