1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** `ServerConfig.EnableAPIAuth` carries two opposed meanings ("auth required" vs "auth already done"), held together only by a handler-side guard
3. **Issue:** `handler_feed.go` mutates `EnableAPIAuth` from "require auth" to "skip auth" after successful HTTP-layer authentication, so `feed.Server` cannot distinguish "auth is disabled for this connection" from "auth already succeeded elsewhere"; the difference survives only because a guard in the handler happens to filter failed-auth requests before the server is constructed.
4. **Severity:** S4 (no runtime defect today; design ambiguity in a security-relevant path that invites a future auth-bypass bug)
5. **Location:** `services/core/internal/api/handlers/handler_feed.go:29-60,71-79`; `services/core/internal/feed/server.go:28-37,50-58,83-89,277`
6. **Expected:** An explicit `Authenticated bool` on `feed.ServerConfig` should state "this connection already proved identity at the HTTP layer", leaving `EnableAPIAuth` to mean only "frame authentication is required" and `SkipOriginCheck` to be an explicit per-path choice — one flag, one meaning, per call site.
7. **Actual:** `handler_feed.go:37-40` and `:49-50` set `EnableAPIAuth = false` / `APIKey = ""` (and `SkipOriginCheck = true` only in the API-key path) to signal "already authenticated". `feed.Server` reads `EnableAPIAuth = false` as "no auth frame required" (`server.go:83-89`) and treats `SkipOriginCheck = false` as "check origin" (`server.go:55`). The handler-side guard at `handler_feed.go:57-60` (`if !serverConfig.EnableAPIAuth && !authenticated`) is the only thing preventing an unauthenticated request from reaching the server with `EnableAPIAuth = false`, i.e. with anonymous read access to the whole change feed.
8. **Reproduction:** Source trace of the two meanings of `EnableAPIAuth=false` reaching `feed.Server` (all HTTP-level auth for `/feed` lives in the handler; `custommiddleware.CombinedAuth` explicitly exempts `/feed` at `middleware/middleware.go:180`):
    - `handler_feed.go:25-28` — `feedServerConfig()` copies `cfg.EnableAPIAuth` into the server config; `SkipOriginCheck` starts zero (`false`); `APIKeyValidator` is wired only when `h.adminAuth != nil`.
    - **Meaning A — "already authenticated":** if the static/managed API key validates (`:30-40`), the handler sets `authenticated = true`, then `EnableAPIAuth = false`, `APIKey = ""`, `SkipOriginCheck = true`. If the API key failed but the admin session validates with a trusted Origin (`:42-51`), it sets `authenticated = true`, then `EnableAPIAuth = false`, `APIKey = ""` (note: `SkipOriginCheck` stays `false`, so the server re-runs the origin check at `server.go:55` via `AllowedOrigin` — an already-passed check, and an asymmetry between the two "already authenticated" flavors).
    - **Meaning B — "auth disabled":** when `cfg.EnableAPIAuth` is `false`, the value passes through untouched. A request that fails session auth (or arrives with `adminAuth == nil`) still has `authenticated == false`; only the guard at `:57-60` converts it to 401. **Without that guard, the request would fall through to `server.ServeHTTP` (`:61-68`) with `EnableAPIAuth = false`, meaning "no auth frame required" (`server.go:83-89`) — an unauthenticated feed subscription. So yes: the guard is the sole separator between the two meanings, and it never fires for mutation-produced `false` (those always carry `authenticated == true`); its only live effect is exactly the auth-disabled-but-not-authenticated case.**
    - Therefore, as written, a request that FAILED authentication cannot reach `feed.Server` with `EnableAPIAuth = false` on any path — the code is currently sound. But that soundness is not enforced by the `feed.Server` API; it is re-established by hand in every guard.
    - The same split shows in duplicated logic: `handler_feed.go:53-56` re-implements `server.go:50-54` (503 when `EnableAPIAuth` with no key/validator). That guard is reachable **only** in the not-authenticated path: if either auth path had succeeded, `EnableAPIAuth` would already be `false` by `:53`. It is additionally constrained to `adminAuth == nil` (else `APIKeyValidator` is non-nil), and "EnableAPIAuth=true with empty key" is fatal at startup in production (`cmd/atlas_core/main.go:134-137`, `internal/config/api_auth.go:15-22`), so the guard mainly makes a misassembled `Handler` observable; `feed.Server` carries the same check a third time.
    - Corroborating tests: `internal/api/handlers/handler_feed_test.go:100-124` (`TestFeedRejectsUnauthenticatedWhenAPIAuthDisabled` — auth "disabled" still 401s an unauthenticated request, showing the handler's flag means "frame/key auth", not "whether auth is required"); `internal/feed/server_test.go:199-299,383-397` exercise `EnableAPIAuth=true` frame-auth behavior and the server-side 503; `server_test.go:349-381` covers the `SkipOriginCheck=false` origin rejection. `handler_feed_integration_test.go:157-216` (`TestFeedAPIKeyTakesPrecedenceOverSessionOrigin`) exercises Meaning A's `SkipOriginCheck=true` mutation end-to-end.
9. **Notes:** The code is currently sound — an exhaustive trace of `handler_feed.go` shows every path reaching `feed.Server` with `EnableAPIAuth=false` also carries `authenticated == true`, and failed-auth requests are 401'd at `:57-60` before the server is constructed. The confirmed defect is the design: one field encodes two opposed invariants ("authentication is required" and "authentication is already done"), the invariant is split across two components that read the field differently, and correctness depends on the handler remembering to set `authenticated` plus two extra mutations (`APIKey = ""`, and `SkipOriginCheck` only for the key path) in every future auth path — none of which the compiler or `feed.Server` enforces. An explicit `Authenticated bool` on `ServerConfig` (server skips the auth frame iff `Authenticated`; `EnableAPIAuth` keeps meaning "require frame auth"; origin suppression made explicit per path) would collapse the guard at `:57-60`, the `APIKey = ""`/`SkipOriginCheck` mutations, and the duplicated 503 check into one readable contract. Severity reflects "sound now, ambiguous design": treat as a targeted refactor, not a security incident. Verification was by source trace plus reading the existing tests; no Go toolchain was available in this environment to execute them (`go: command not found`).
