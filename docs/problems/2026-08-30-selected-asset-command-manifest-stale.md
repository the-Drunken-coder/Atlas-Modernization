# Problem Report

1. **Time & Date:** 2026-08-30T14:57:34Z
2. **Name:** Selected Asset command manifest stays stale across runtime changes
3. **Issue:** The Command Interface reloads selected Asset detail only when the selected Asset ID changes, even though Atlas Core advances the Entity version and emits an Entity update when that Asset runtime becomes ready or stops. Feed and snapshot resources do not contain the read-only runtime `command_manifest`, so the selected detail can remain stale for the lifetime of the selection.
4. **Severity:** S3 (Moderate)
5. **Location:** Atlas Command Interface, `surfaces/command-interface/src/features/MapConsole.tsx` (`selectedEntityDetails` effect and merge); Atlas Core runtime manifest changes, `services/core/internal/actions/task_runtime.go`, `services/core/internal/actions/change_hook.go`, and `services/core/internal/api/handlers/handler_entity.go`
6. **Expected:** When the selected Asset's runtime becomes ready, the interface reloads its detail and exposes the current `command_manifest`. When that runtime stops, the interface removes the manifest and disables command selection. Both transitions should converge without requiring the operator to deselect and reselect the Asset.
7. **Actual:** `MapConsole`'s detail-loading effect depends on `atlas.loadEntityDetails`, `commandDetailsRequired`, and `selectedSnapshotEntityId`, but not the selected Entity version or any runtime-change signal (`MapConsole.tsx:106-129`). The selected detail is then merged whenever its ID matches (`MapConsole.tsx:139-144`). Core's `CompleteRuntimeRegistration` updates the runtime and records the versioned Entity feed change (`task_runtime.go:277-283`), while `StopRuntime` clears the manifest and records the same kind of change (`task_runtime.go:170-187`); the event serializes the Entity without `command_manifest` (`change_hook.go:128-143`). Only `GET /entities/{id}` decorates the response with the current ready manifest (`handler_entity.go:54-69`). Consequently, a selected Asset that was stopped when its detail was loaded keeps an undefined manifest after a ready update and continues to show no commands, while a selected Asset that was ready when loaded keeps its old manifest after a stop and continues to offer commands that Core rejects.
8. **Reproduction:**
   1. Start Atlas Core with a task catalog and create an Asset. Register its runtime while it is not ready, then select that Asset in the Command Interface. The detail request returns no `command_manifest`, and the selected entity is held with `command_manifest: undefined` while the selected ID remains unchanged.
   2. Make the same runtime ready with a non-empty manifest. Core updates `asset_runtimes`, advances the Entity version, and emits an Entity update, but the feed resource has no manifest. The existing detail-loading effect does not rerun because the ID did not change. Open Commands and observe the stale “This Asset has no Commands” state; deselecting and reselecting causes the GET detail request and reveals the manifest.
   3. In a separate run, select an Asset after its runtime is ready and let the detail request return a non-empty manifest. Stop that runtime. Core clears the runtime manifest and emits the versioned Entity update, but `selectedEntityDetails` still has the old manifest and its ID still matches. Observe that the interface continues to display the old command as available; submitting it reaches Core and is rejected because no runtime is ready.
   4. The focused existing test `npm test --workspace surfaces/command-interface -- src/features/MapConsole.test.tsx` passes all 29 tests, including the telemetry snapshot replacement case that explicitly expects one detail request. No existing test covers a ready/stop runtime transition for a selected Asset.
9. **Notes:** Confirmed by source trace at commit `804bf32fa733ca582f931816f58cdb5aae218701`; no product or test files were changed. The smallest fix is to invalidate or reload selected Asset detail when its selected snapshot Entity version changes for a runtime event, preserving request cancellation and ID guards. A focused UI regression should cover both stopped-to-ready and ready-to-stopped transitions, including command availability and detail-request counts. Alternatively, the feed could carry a runtime manifest, but that would duplicate the authoritative read-only detail and conflict with Core's current serialization boundary.
