# Core request acceptance drifts from the canonical Atlas Protocol

1. **Time & Date:** 2026-07-30T08:33:00Z
2. **Original Audit Finding:** 8
3. **Validation Status:** Confirmed against `main` at `2426bb6`.
4. **Name:** Core request acceptance drifts from the canonical Atlas Protocol
5. **Affected Surface & Severity:** Atlas Core entity/task/object request handlers and Atlas Protocol request schemas; S3 (Moderate). Generated clients and protocol validators can disagree with requests that Core accepts or rejects.
6. **Current vs. Expected:** The canonical validators reject empty entity, task, and object PATCH bodies, while Core decodes `{}` and returns the unchanged resource as a successful no-op. The canonical task-create schema accepts any non-empty `status`, while Core only permits `pending`. The schema also rejects `null` for non-nullable update fields, but direct decoding into Core pointer, map, and slice fields collapses many explicit nulls to the same zero value as absence and accepts them as no-ops. Core and the canonical protocol should accept and reject the same wire bodies. Intended nullable fields (`entity.alias`, `entity.subtype`, and `task.entity_id`) must continue to distinguish null from absence.
7. **Concrete Source Evidence:** `atlas_protocol/schema/jsonschema/atlas.schema.json:301-338`, `:1107-1143`, and `:1593-1626` set `minProperties: 1` for all three update requests. Core instead has explicit no-op paths in `atlas_core/internal/actions/entity_actions.go:238-287`, `task_actions.go:222-280`, and `object_actions.go:189-206`. `atlas_protocol/schema/jsonschema/atlas.schema.json:1360-1422` defines task-create `status` as a `NonEmptyString`; `atlas_core/internal/actions/task_status.go:24-35` rejects every initial status except `pending`. Request fields in `atlas_core/internal/api/handlers/handler_requests.go:34-40`, `:122-128`, and `:180-189` use ordinary pointers/maps/slices for non-nullable fields, while only `nullablePatchString` at `handler_entity.go:109-137` preserves the intended null/absence distinction. The handlers call `decodeJSONRequestBody` and action methods directly; they do not run the canonical request validators.
8. **Reproduction / Static Proof:** A temporary Go probe against the public protocol validator returned `minProperties: got 0, want 1` for `ValidateEntityUpdateRequest({})`, `ValidateTaskUpdateRequest({})`, and `ValidateObjectUpdateRequest({})`; it returned no error for `ValidateTaskCreateRequest({"task_id":"t","status":"acknowledged"})`; and it rejected `{"status":null}`. The generated TypeScript validators returned the same `false, false, false, true, false` matrix. In Core, `{}` maps to each action's documented no-op branch; task create reaches `normalizeInitialTaskStatus` and rejects `acknowledged`; and Go JSON decoding maps examples such as task `status:null`, entity `entity_type:null`, and object `path:null` to nil just like absence. Focused handler tests for intended nullable fields and task-status defaulting passed with `go test ./internal/api/handlers -run 'TestNullablePatchStringDistinguishesAbsentNullAndValue|TestUpdateTaskRequestEntityIDDistinguishesAbsentNullAndValue|TestCreateTaskRequestDefaultsStatusToPending' -count=1`.
9. **Root Cause:** Core validates decoded domain parameters and final resource blobs, but it does not validate the original request shape against the canonical request definitions. Lossy Go decoding erases property presence for ordinary pointer, map, and slice fields. Separately, the schema never encoded Core's existing initial-task-status invariant.
10. **Simplest Correct Proposed Solution:** Make the wire contract and Core agree at the HTTP boundary: constrain an explicitly supplied task-create status to `pending` in the canonical schema, and reject empty PATCH objects plus explicit nulls for non-nullable fields before lossy request mapping. Reuse the canonical request validator at that boundary rather than duplicating field lists in actions. Preserve the three intentionally nullable patch fields.
11. **Acceptance Criteria / Regression-Test Plan:** Add a conformance matrix exercised by both protocol validators and Core endpoints. It must reject `{}` for all three PATCH types; reject `acknowledged` on task create in both places; reject explicit null for every non-nullable update property; accept omission of optional properties; accept null for entity alias/subtype and task entity_id with the documented clearing behavior; and accept representative valid partial updates. Extend Core request-conformance integration coverage beyond its current entity-only subset to tasks and objects.
12. **Scope / Non-Goals:** Do not change task lifecycle rules, add compatibility behavior for nonexistent users, or require protocol validation inside domain actions. This note does not cover response conformance or semantic validation of final stored blobs.
13. **Overlaps:** Findings 10 and 11 are also protocol/JavaScript validator boundary issues, but concern numeric precision and recursion rather than Core request acceptance.
