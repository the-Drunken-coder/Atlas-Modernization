# Problem Report

1. **Time & Date:** 2026-09-17T15:33:17Z
2. **Name:** Meshtastic process acceptance serializes independent phases in one test
3. **Issue:** The compiled-process acceptance is one large `node:test` case covering rejected startup, rejected join, authenticated joining, optional private-delivery recovery, application settlement, publication, pending shutdown, and cleanup. A failure in any earlier phase exits the main sequence, so later independent checks are not executed in that run and the failure gives poor isolation.
4. **Severity:** S4 (Minor)
5. **Location:** `packages/meshtastic-link/acceptance/process-acceptance.ts:137-715`; timeout declarations at `packages/meshtastic-link/acceptance/process-acceptance.ts:133-138`; CI invocation at `.github/workflows/meshtastic-link-acceptance.yml:19-50`
6. **Expected:** Independent acceptance phases should remain independently observable, or the harness should report explicit phase-level failures without suppressing later independent checks. The timeout accounting should make the real upper bound obvious.
7. **Actual:** There is exactly one top-level `test(...)` declaration at line 137, with a 579-line callback through line 715. Assertions and waits are serial inside one `try` block. Any rejection reaches the `catch` at lines 669-671, runs cleanup, and is rethrown at line 714; control never reaches subsequent phases. The source contains 25 exact `15_000` occurrences: one shared HTTP timeout constant at line 133 and 24 explicit phase/deadline arguments in the test body. The body also has six `30_000`, seven `5_000`, and one `2_000` literal timeout arguments. Some mapped waits are parallel, so this is not 25 times 15 seconds of wall time, but the test-level timeout is explicitly 810,000 ms at lines 134-138, or 13.5 minutes. The source comment documents a scheduled fault path of 776 seconds, plus 10 seconds of cleanup and 24 seconds for evidence writes, which contradicts the reported approximately six-minute worst case. The CI job itself permits 20 minutes (`meshtastic-link-acceptance.yml:19-26`), and `fail-fast: false` only separates matrix cases, not phases inside this test.
8. **Reproduction:**
   1. Run `npm run test:acceptance --workspace @the-drunken-coder/atlas-meshtastic-link` in a dependency-complete checkout.
   2. Cause any earlier wait or assertion to fail, such as the mismatched-key challenge check at `process-acceptance.ts:264-273` or the active/joined status checks at `process-acceptance.ts:330-342`.
   3. Observe that the callback stops at that failure, executes only the cleanup/evidence path in `finally`, and rethrows after cleanup. The later application, publication, pending-shutdown, and shutdown assertions are not run in that invocation.
   4. Independently inspect the timeout literals and the `timeout: processTestTimeoutMs` option. The six-minute claim cannot be reproduced from the current source: the configured upper bound is 810 seconds, with the scheduled fault-path budget documented as 776 seconds before cleanup/evidence overhead.
9. **Notes:** Confirmed test-maintenance/debugging cost, not a product correctness defect. The test intentionally exercises a broad end-to-end lifecycle and preserves partial artifacts, but partial artifacts do not execute or pass/fail the skipped assertions. The 15-second count is a syntactic count, not a claim that all waits run serially: `Promise.all`/`Promise.allSettled` runner waits are concurrent, and `waitForJSON` shares a deadline across polling attempts. Existing README documentation describes this as one compiled-process acceptance run (`packages/meshtastic-link/README.md:166-182`), and no subtests or phase-level test declarations exist. Runtime execution was not attempted because this clean worktree has no installed `node_modules`; source accounting and control-flow inspection were completed. A focused split or phase-aware harness would improve isolation while preserving the end-to-end scenario.
