1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** Dispatcher couples data-retention cleanup to live change-feed delivery loop
3. **Issue:** The change-feed dispatcher runs movement-history pruning and change-log pruning synchronously inside its LISTEN connection loop; slow or failing cleanup delays live updates or tears down feed delivery entirely.
4. **Severity:** S4 (structural robustness, latent until data volume or DB latency grows)
5. **Location:** services/core/internal/feed/dispatcher.go:78-104 (prunes at dispatcher.go:82-96); services/core/internal/actions/movement_history.go:258-262 (PruneMovement); services/core/internal/actions/change_retention.go:22-90 (PruneChangeRecords)
6. **Expected:** Retention cleanup should run in its own background loop that cannot affect change-feed delivery latency or availability, with cleanup failures retried/logged instead of disconnecting the feed — the same shape already used by the storage deletion reconciler (`runStorageDeletionReconciler`, services/core/cmd/atlas_core/main.go:44-63, started at main.go:209 as an independent goroutine that logs and continues on error).
7. **Actual:** In `runConnection`, each iteration does drain → PruneMovement (every 30s, 5s timeout, failure log-only) → PruneChangeRecords (hourly, error returned from runConnection) → WaitForNotification. While either prune runs, notification processing can only wait — drain and prunes execute strictly before `conn.WaitForNotification` (dispatcher.go:97), so no live event is dispatched during cleanup. If PruneChangeRecords fails, the error is returned out of runConnection (dispatcher.go:92-94), the dispatcher logs "Atlas change dispatcher disconnected" and re-enters the Run reconnect loop with 1s→30s exponential backoff (dispatcher.go:35-65), pausing live feed delivery for all subscribed clients until reconnect.
8. **Reproduction:** Source trace: each `runConnection` iteration performs drain then both prunes (dispatcher.go:79-96) before blocking on notification (dispatcher.go:97-99); `Run` reconnects with backoff on any runConnection error (dispatcher.go:37-51). Injecting a PruneChangeRecords failure (e.g., mock/stub returning an error or a forced DB error during the DELETE batch) makes runConnection return the error, shutting the LISTEN connection down and pausing live feed delivery through the backoff cycle — despite the underlying notification transport being healthy.
9. **Notes:** Asymmetric failure semantics: movement prune failure is log-only ("Movement history retention cleanup failed", dispatcher.go:87-89) and self-retries; change prune failure is fatal to the connection and triggers the reconnect loop. Both prunes are bounded-batch DELETEs — PruneMovement deletes up to 10000 leading rows from entity_movement_samples (movement_history.go:259-260), and PruneChangeRecords loops 500-row DELETE batches against atlas_change_events inside transactions that take `FOR UPDATE` on the change-clock row (change_retention.go:52-89), so queries are plausibly fast at current (small) scale; the risk is latency growth with data and the structural coupling, not an outage today. A separate background cleanup loop precedent exists: the storage deletion reconciler runs as its own goroutine with a ticker, warn-log-and-continue error handling (main.go:44-63, 209), matching the finding's suggested fix.
