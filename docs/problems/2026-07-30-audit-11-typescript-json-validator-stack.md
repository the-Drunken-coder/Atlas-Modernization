# Generated TypeScript JSON validation can overflow the call stack

1. **Time & Date:** 2026-07-30T08:33:00Z
2. **Original Audit Finding:** 11
3. **Validation Status:** Confirmed against `main` at `2426bb6`.
4. **Name:** Generated TypeScript JSON validation can overflow the call stack
5. **Affected Surface & Severity:** Public Atlas Protocol TypeScript validators and Atlas SDK request/response validation for `extra`, custom components, and other `JSONValue` fields; S3 (Moderate). A deeply nested but protocol-valid, sub-request-limit document fails validation with an uncaught `RangeError` at the validator boundary.
6. **Current vs. Expected:** `atlasProtocolIsJSONValueInternal` recursively descends every array and object member. On the repository-required Node 24 runtime, a depth-2,000 nested object validates while depth 3,000 throws `RangeError: Maximum call stack size exceeded`; Node 25.9.0 independently failed between depths 7,500 and 8,000. An SDK object-detail response containing a valid deeply nested value also rejects with `RangeError`. Validation should return a boolean (or the SDK's normal validation error) for every payload within the supported body limits rather than exhaust the JavaScript call stack.
7. **Concrete Source Evidence:** The generator emits direct recursion in `atlas_protocol/tools/internal/artifacts/typescript_runtime_helpers.go:107-141`; the generated copy is at `atlas_protocol/generated/typescript/index.ts:625-655`. Object request/detail validators invoke this helper for `extra` (`index.ts:466-475`). The SDK composes the generated object-detail validator at `atlas_sdk/src/validation.ts:57-61` and calls it on public object reads at `atlas_sdk/src/sync-engine.ts:298-306`.
8. **Reproduction / Static Proof:** Using bundled Node 24.14.0 and the public generated `isObjectCreateRequest({object_id:"o", extra:{nested:<nested object>}})`, depths 1,000 and 2,000 returned `true` while depths 3,000 through 8,000 threw `RangeError`. A separate Node 25.9.0 temporary Vitest probe reproduced the public-validator failure at depth 8,000, then built a sub-request-limit object-detail JSON response iteratively, let `Response.json()` parse it through `AtlasClient.objects.get("o", {fresh:true})`, and observed the same `RangeError` from SDK validation. `vitest run atlas-deep-json.test.ts --root /tmp --environment node` passed both assertions. The exact stack threshold is runtime-dependent; the bounded failure is not.
9. **Root Cause:** Cycle detection uses a `WeakSet`, but traversal itself remains recursive and consumes one JavaScript stack frame per JSON nesting level.
10. **Simplest Correct Proposed Solution:** Replace recursive JSON-value traversal in the generated runtime helper with a small iterative worklist/enter-exit traversal that preserves finite-number checks, plain-record checks, and cycle rejection. Do not add a speculative general validation framework.
11. **Acceptance Criteria / Regression-Test Plan:** Generated public validators must return `true` for an acyclic valid `JSONValue` at depth 3,000 on Node 24 without throwing, return `false` for cycles and non-JSON values, and retain ordinary object/array coverage. Add an SDK object-detail test using a sub-request-limit serialized response at the same depth and assert the read succeeds. Keep generator artifact checks deterministic.
12. **Scope / Non-Goals:** This note does not require unlimited payload sizes, change HTTP body limits, or claim that documents nested thousands of levels deep are normal application data. It addresses valid payloads that fit existing limits and must not crash the validator.
13. **Overlaps:** Finding 10 concerns numeric precision in the same generated surface. Finding 5 may require sanitizing errors before display, but sanitization does not prevent this validation failure.
