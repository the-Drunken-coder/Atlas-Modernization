# Problem Report

1. **Time & Date:** 2026-08-30T15:02:10Z
2. **Name:** Selected-entity detail requests remain active after selection changes
3. **Issue:** The Command Interface starts a fresh Asset detail request when an Asset is selected, but the effect cleanup only ignores the eventual result. It does not provide an `AbortSignal` to the SDK request, so a request for an Asset that is no longer selected continues using browser and Core resources.
4. **Severity:** S4 (Minor)
5. **Location:** Command Interface, `surfaces/command-interface/src/features/MapConsole.tsx` (`selectedEntityDetails` effect at lines 106-130), `surfaces/command-interface/src/state/atlas-context.tsx` (`loadEntityDetails` at lines 26 and 171-175), and `surfaces/command-interface/src/atlas/data-source.ts` (`loadEntityDetails` at lines 28 and 58)
6. **Expected:** When the selected Asset changes or the map console unmounts, the detail request for the previous selection should be cancelled so the browser and Core can release work that cannot affect the current UI.
7. **Actual:** `MapConsole` sets a local `cancelled` flag in the effect cleanup and checks it before committing success or failure, but it calls `atlas.loadEntityDetails(selectedSnapshotEntityId)` without a signal. The context and data-source interfaces accept only an entity ID, and the real source calls `client.entities.get(entityId, { fresh: true })` without `signal`. The SDK therefore keeps the request active until it completes or its normal request timeout expires (30 seconds by default while waiting for response headers). Rapidly alternating visible Assets can accumulate concurrent stale GETs; each still reaches Core and can hold a request handler and database work while it is pending. The current SDK response-body timeout gap can extend body reads further, but that is a separate transport defect.
8. **Reproduction:**
   1. Enable a non-empty command catalog and open the authenticated Command Interface with at least two visible Asset entities.
   2. Instrument `fetch` or the Core test server to leave `GET /entities/{id}` pending before response headers. Select Asset A, then select Asset B, then alternate between them several times while each request remains pending.
   3. Observe that the first request's promise remains pending after the selection effect cleanup runs. Its `AbortSignal` is absent from `loadEntityDetails`, `AtlasDataSource`, and the real `client.entities.get` call, so no abort event reaches `fetch`; every pending request remains active until the server responds or the SDK's default 30-second header timeout fires.
   4. The UI does not display an incorrect stale manifest because the cancellation flag suppresses stale state updates. The resource failure is the accumulation of obsolete requests. The existing focused test `npm test --workspace @the-drunken-coder/atlas-command-interface -- src/features/MapConsole.test.tsx --run` passes all 29 tests; its deferred request test covers telemetry snapshot replacement and explicitly expects one request to remain alive, but no test covers selection-change abort or request-signal propagation.
9. **Notes:** This is a bounded resource leak rather than a stale-render correctness failure, so it is S4. The smallest fix is to thread an optional `AbortSignal` through `AtlasContextValue`, `AtlasDataSource`, and `client.entities.get`, create one controller per detail-loading effect, and abort it in cleanup while treating the resulting abort as an expected outcome. Add a focused test that changes selection and asserts the previous request's signal is aborted, while preserving the existing telemetry snapshot behavior that intentionally does not restart the same-entity request.
