# Problem Report

1. **Time & Date:** 2026-08-30T14:58:12Z
2. **Name:** Core and SDK disagree on canonical resource IDs
3. **Issue:** Core accepts resource IDs with surrounding whitespace and trims them before storage, while the SDK retains the caller's raw ID for write-response comparisons and feed subscription keys.
4. **Severity:** S3 (Moderate)
5. **Location:** Atlas Core `services/core/internal/actions/validation.go` and `services/core/internal/feed/hub.go`; Atlas SDK `packages/sdk/src/client.ts`, `packages/sdk/src/sync-engine.ts`, and `packages/sdk/src/subscriptions.ts`
6. **Expected:** A resource ID has one canonical representation across HTTP writes, feed subscriptions, cache keys, response checks, and delivered events. A caller using an otherwise valid ID with surrounding whitespace should either receive a consistent trimmed ID everywhere or be rejected before the request is committed.
7. **Actual:** `ValidateResourceID` validates the input and `SanitizeID` trims it before Core writes (`validation.go:30-42, 96-98`). A create request such as `{"entity_id":" asset-1 ","entity_type":"asset"}` therefore commits and returns `asset-1`, but `AtlasClient.entities.create` passes the raw input as `expectedID` (`client.ts:107`) and `SyncEngine.writeResource` compares it exactly (`sync-engine.ts:498-508`), so the SDK throws after Core has committed the resource. The same mismatch applies to object creation. For feed subscriptions, Core trims `msg.ID` when building its subscription (`hub.go:138-160`), while SDK subscription keys retain the raw ID (`subscriptions.ts:25-35`) and `matchesSubscription` uses strict equality (`subscriptions.ts:68-80`); a canonical event for `asset-1` therefore does not reach a watcher subscribed with `asset-1`.
8. **Reproduction:**
   1. Send a valid Core create request with a surrounding-whitespace resource ID, for example `POST /entities` with `{"entity_id":" asset-1 ","entity_type":"asset"}`. Trace `EntityActions.Create` or `ObjectActions.Create`: validation succeeds, `SanitizeID` yields `asset-1`, and the transaction writes that canonical ID.
   2. Call the SDK with `client.entities.create({ entity_id: " asset-1 ", entity_type: "asset" })` (or the equivalent object request), using a transport that returns the successful Core resource with ID `asset-1`. Observe rejection with `Atlas entity response id asset-1 does not match requested id  asset-1 ` even though the resource was committed.
   3. Subscribe and watch with `{ filter: "id", resource_type: "entity", id: " asset-1 " }`, then deliver a feed event whose canonical ID is `asset-1`. Observe that `matchesSubscription` returns false and the watcher is not called. The isolated SDK probe produced `{"key":"[\"id\",\"entity\",\" asset-1 \"]","matches":false}`.
9. **Notes:** This is one cross-boundary canonicalization defect with both write and feed-observation symptoms. The smallest coherent fix is to establish one ID normalization policy at the SDK/Core boundary and apply it to write expected-ID checks, subscription keys/matching, and cache/path identity; alternatively reject surrounding whitespace consistently before any write. Add focused tests for entity and object create, and for feed delivery when the subscription input contains surrounding whitespace. The existing fake Core uses generated TypeScript predicates, which do not model the real Core's trimming behavior, so an integration or contract test against the Go Core is needed.
