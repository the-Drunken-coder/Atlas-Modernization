1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** Instance-token reuse detection relies on exact error-message strings across the Go/TS module boundary
3. **Issue:** Both the Go retry-recovery path and the command-interface UI detect token reuse by comparing human-readable message text. The contract works today but is latent: any wording change to either string silently breaks retry recovery or UI token-reuse handling, and no test pins the wording contract across the Go/TS boundary.
4. **Severity:** S4 (fragile string contract that currently works; failure is triggered by any future wording edit with no test guarding it)
5. **Location:**
   - `services/core/internal/actions/entity_actions.go:216-219` (`isResourceInstanceTokenReuse` compares `ValidationError.Message == "resource instance token has already been used"`)
   - `services/core/internal/actions/entity_actions.go:175-177` (matches, then re-wraps as `"resource instance token has already been used for this entity instance"`)
   - `services/core/internal/actions/resource_instance_token.go:57` (produces the base string)
   - `surfaces/command-interface/src/atlas/data-source.ts:399-404` (`isResourceInstanceTokenReuse` checks `error.message.includes("resource instance token has already been used for this entity instance")`)
6. **Expected:** The error should carry a stable machine-readable code (e.g. a dedicated protocol `ErrorCode` for resource-instance-token reuse) that both Go and TS can match on. The mechanism already exists and is unused here: `ActionError.Code protocol.ErrorCode` (`services/core/internal/actions/action_errors.go:15,38`) is populated per error type and flows straight through the HTTP layer as `error_code` (`services/core/internal/api/handlers/handler_response.go:92-101`, `writeValidationError` sets `ErrorCode: validationErr.Code`). However, both token-reuse errors are created via `NewValidationError`, which assigns the generic `protocol.ErrorCodeValidationError` shared by dozens of unrelated errors (`packages/protocol/generated/go/atlasprotocol/types.go:42`), so code alone cannot discriminate the case today. The fix should reuse this existing field with a dedicated code (or a dedicated `ErrorCode*` in the schema, via `packages/protocol` regeneration), not add a new channel.
7. **Actual:** Go matches `ValidationError.Message ==` exactly and the UI matches `error.message.includes(...)`; the UI does already filter on `status === 400 && error.errorCode === "VALIDATION_ERROR"`, but because that code is generic, the discriminating check is the message text. Contract is pinned only inside each side's own tests: `services/core/internal/integration/ifmatch_test.go:181` transitively pins the internal Go match (it drives the real flow and asserts the re-wrapped string), and `surfaces/command-interface/src/atlas/data-source.test.ts:654,710,773,783,818,862,928` pin the TS side against local mocks. Nothing ties the mock strings to the Go producer — a wording edit in Go breaks production UI handling while all TS tests still pass.
8. **Reproduction:** Trace: `resource_instance_token.go:57` returns `NewValidationError("resource instance token has already been used")` → `entity_actions.go:174-176` matches that exact message via `isResourceInstanceTokenReuse` (line 216-219) and re-wraps to `"resource instance token has already been used for this entity instance"` → HTTP layer emits it with `error_code: "VALIDATION_ERROR"` (handler_response.go:97) → `data-source.ts:403` identifies it via `message.includes(...)`. Editing either string makes the Go re-wrap (or the UI recovery) stop firing silently. Note the substring semantics are load-bearing: `data-source.test.ts:889` asserts the base message without the "for this entity instance" suffix must NOT trigger recovery, so `includes` must stay a substring match — an alternative wording change could likewise invert that behavior.
9. **Notes:** Exact strings and their three (plus one consumer) locations:
   - `"resource instance token has already been used"` — produced at `services/core/internal/actions/resource_instance_token.go:57`; matched at `services/core/internal/actions/entity_actions.go:218`; referenced as the non-recovery case in `surfaces/command-interface/src/atlas/data-source.test.ts:889`.
   - `"resource instance token has already been used for this entity instance"` — produced at `services/core/internal/actions/entity_actions.go:176`; consumed at `surfaces/command-interface/src/atlas/data-source.ts:403`; pinned in `services/core/internal/integration/ifmatch_test.go:181` and across `surfaces/command-interface/src/atlas/data-source.test.ts` (mocks only).
   - No other message-matching instances found: a search for `.includes(` on error messages in `surfaces/command-interface/src` and `== "..."` on `Message` in `services/core` turned up only these instances (all other `.includes(` hits were unrelated array/URL/keyboard checks). Recommended fix: add a dedicated protocol error code for token reuse and match on `errorCode` on both sides.
   - Verified current strings are consistent end to end (same literal in producer, Go matcher, and UI matcher), so the defect is latent fragility, not an active break.
