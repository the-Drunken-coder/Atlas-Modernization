1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** Single transactional change-clock row serializes every versioned write, capping aggregate write throughput
3. **Issue:** All versioned mutations across Core (entity create/update/delete, object create/update/upload, task create, task transitions, runtime registration/stop/drain) and entity check-ins contend on one `FOR UPDATE` lock of the `atlas_change_clock` singleton row acquired at transaction start; the lock is held until COMMIT, so total committed write throughput is bounded by that one serialization point.
4. **Severity:** S5
5. **Location:** `services/core/internal/actions/write_version.go:12-31` (beginChangeTx), `:33-54` (reserveChangeVersions), `:17-21` (documented lock-order comment in code); callers: `internal/actions/entity_actions.go:158,359,500`, `internal/actions/object_actions.go:70,228`, `internal/actions/object_upload.go:23`, `internal/actions/task_create.go:48`, `internal/actions/task_transition.go:262`, `internal/actions/task_runtime.go:75,144,228,434,535`; check-in path `internal/actions/entity_checkin_actions.go:38-49` → `entity_actions.go:359`
6. **Expected:** If check-in/asset growth ever needs higher throughput: shard or batch version reservation, move the clock increment to a commit-ordering stage after resource writes, or partition hot paths (e.g. check-in vs lifecycle writes) — while preserving the documented contiguous-version/push-and-recovery invariants. Per `docs/design-decisions/2026-06-10-global-write-version-lock.md`: "Higher write throughput would require changing the cursor design rather than quietly bypassing the counter row."
7. **Actual:** `beginChangeTx` opens every versioned write transaction with `SELECT version FROM atlas_change_clock WHERE singleton FOR UPDATE` (write_version.go:23) before any per-object advisory lock, intent row, or resource row. The row lock persists for the whole transaction — the serialization window spans all work (resource row writes, event-log append) from BEGIN to COMMIT, not just the version increment (`reserveChangeVersions` at :42-47 is safe because the lock is already held). Transactions therefore commit one-at-a-time in clock order. The check-in handler calls `EntityActions.Update` directly, which calls `beginChangeTx` with label `"entity update"` (entity_actions.go:359) — so position/heartbeat check-ins absolutely go through the same global lock.
8. **Reproduction:** Source trace above; coverage exists but no throughput ceiling measurement: `internal/actions/write_version_concurrency_test.go` has `TestCreateDeleteAndUniqueValueRacesDoNotDeadlock` (:13) and `TestVersionedMutationsWaitForClockBeforeResourceRows` (:93) — these prove lock ordering and no-deadlock, not sustained writes/sec. `internal/actions/task_runtime_benchmark_test.go` `BenchmarkRuntimeRestartFencing` (:12-45) measures runtime-registration drain time at 100/1,000/10,000 task fixtures against a real pool — indirectly constrained by the same lock but never intended to quantify the ceiling. No benchmark measures aggregate committed writes/sec. Run: `go test ./internal/actions -run Write` against a Postgres test pool (test helpers in package).
9. **Notes:** This is deliberate and documented, not a bug. Primary decision: `docs/design-decisions/2026-06-10-global-write-version-lock.md` — "Writes remain intentionally serialized from transaction start, but committed versions are contiguous and one durable log drives both push and recovery" and the explicit consequence that throughput changes need a cursor redesign. The fat-events decision `2026-06-12-change-feed-websocket-fat-events.md:10` says "the previous global-write-lock decision is historical context rather than the current mechanism" — but review of the current decision clarifies this means the *old sequence/advisory-lock mechanism* was superseded by the clock row; the global serialization idea itself remains the CURRENT mechanism via `atlas_change_clock` (both texts are consistent; the clock IS the current lock). Corroborating docs: `docs/movement-history-implementation.md:118` acknowledges imports "still serialize against writes to the same Entity" under live change-clock ordering. Check-in path confirmed (see #7), so the review's caution to "measure check-in rates before adding many assets" is valid: per-asset heartbeat/position traffic shares this ceiling with all other writes. Honest framing: measurable ceiling (transactions/sec bounded by lock hold time per transaction), acknowledged in design docs, with unit-level concurrency tests but no throughput benchmark — that absence is the only actionable residual, and S5 reflects greenfield scale where no ceiling has been hit.
