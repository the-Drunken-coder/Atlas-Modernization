# Problem Report

1. **Time & Date:** 2026-08-30T15:01:51Z
2. **Name:** Inbox startup failure leaves MeshCore polling active
3. **Issue:** `MeshCoreTransport.startInbox()` enables the inbox listener and polling timer before its initial `flushInbox()` completes. If the inbox evidence callback rejects during that initial flush, the rejection reaches the caller without marking the transport fatal or stopping the timer. A caller that catches the startup error can therefore continue consuming inbox messages after evidence preservation has already failed.
4. **Severity:** S4 (Minor)
5. **Location:** Atlas FieldLink, `packages/fieldlink/src/radio.ts` (`MeshCoreTransport.startInbox`, `flushInbox`, `#requestDrain`, and `#reportFatal`); `packages/fieldlink/tests/radio.test.ts` (startup evidence failure coverage)
6. **Expected:** A failure to preserve an inbox item during startup should put the transport in the same fatal state as a background evidence failure: stop polling and notify `onFatalError`, with no later inbox items consumed unless the caller explicitly creates a new transport.
7. **Actual:** `startInbox()` sets `#inboxActive`, installs the `MsgWaiting` listener, and starts the 500 ms interval at `radio.ts:253-262`, then awaits `flushInbox()` at line 263. `flushInbox()` calls `#startDrain()` directly at lines 430-434, so an `onInboxMessage` rejection from `#drainInbox()` at lines 486-487 propagates without the catch in `#requestDrain()` at lines 452-456. `#reportFatal()` is therefore not called, `#inboxActive` and the polling listener remain active, and the next interval can start another drain. The failed item has already been removed by `syncNextMessage()` before the callback runs.
8. **Reproduction:**
   1. From the repository root, run this in-memory probe; the callback fails once, then succeeds, and the fake connection contains two inbox messages:

      ```sh
      node --import tsx --input-type=module --eval 'import { MeshCoreTransport } from "./packages/fieldlink/src/radio.ts"; class FakeConnection { messages=[{channelMessage:{channelIdx:2,pathLen:1,txtType:0,senderTimestamp:1,text:"failed-evidence"}},{channelMessage:{channelIdx:2,pathLen:1,txtType:0,senderTimestamp:2,text:"polled-after-failure"}},null]; listeners=new Map(); closed=false; on(e,l){const s=this.listeners.get(e)??new Set();s.add(l);this.listeners.set(e,s)} off(e,l){this.listeners.get(e)?.delete(l)} connect(){return Promise.resolve()} close(){this.closed=true;return Promise.resolve()} getChannel(channelIdx){return Promise.resolve({channelIdx,name:"fieldlink",secret:new Uint8Array([1])})} getChannels(){return Promise.resolve([])} getSelfInfo(){return Promise.resolve({publicKey:new Uint8Array(32),name:"fake",radioFreq:915,radioBw:250,radioSf:10,radioCr:5,txPower:1,maxTxPower:2})} deviceQuery(){return Promise.resolve({firmwareVer:12,firmware_build_date:"",manufacturerModel:""})} getStatsCore(){return Promise.resolve({data:{batteryMilliVolts:4000,uptimeSecs:1,queueLen:0}})} sendChannelData(){return Promise.resolve()} syncNextMessage(){return Promise.resolve(this.messages.shift()??null)} } const connection=new FakeConnection(); const seen=[]; const fatal=[]; let first=true; const transport=new MeshCoreTransport("fake",{channel:2,connection,onInboxMessage:async m=>{seen.push(m.channelMessage?.text);if(first){first=false;throw new Error("evidence sink failed")}},onFatalError:e=>fatal.push(e.message)}); await transport.open(); let startupError="none"; try{await transport.startInbox()}catch(error){startupError=error.message} await new Promise(resolve=>setTimeout(resolve,700)); console.log(JSON.stringify({startupError,seen,remainingMessages:connection.messages.length,fatal,closedBeforeExplicitClose:connection.closed})); await transport.close();'
      ```

   2. Observe `{"startupError":"evidence sink failed","seen":["failed-evidence","polled-after-failure"],"remainingMessages":0,"fatal":[],"closedBeforeExplicitClose":false}`. The startup call fails, but the 500 ms polling interval consumes the second inbox item and no fatal callback runs.
   3. The focused existing suite still passes: `npm test --workspace atlas-fieldlink -- --run tests/radio.test.ts` (`16` tests). Its startup failure assertion at `radio.test.ts:509-543` checks immediately after rejection and does not wait for the polling interval.
9. **Notes:** The default adapter path calls `transport.startInbox({ deliverDatagrams: false })` from `serveAdapter` at `adapter-process.ts:261` and then, when startup fails, its `finally` closes `runtime.node` at lines 386-400; `FieldLinkNode.close()` closes the transport. That bounds the issue for the current adapter startup path, but does not repair the transport's failed-start state for callers that catch the rejection or for a future caller that uses `MeshCoreTransport` directly. The smallest repair is to route the initial flush through the same fatal-error path, stopping polling and reporting the failure before rethrowing it.
