# Problem: SDK recovery evidence mixes telemetry with passing assertions

1. **Time & Date:** 2026-09-17T15:35:00Z
2. **Name:** Keep SDK recovery milestones and configuration metadata out of assertion evidence
3. **Issue:** The SDK recovery acceptance scenario writes phase milestones and its test configuration through the assertion `record()` sink as unconditional passing checks. These entries increase the evidence log without independently validating a contract, making the actual recovery assertions harder to review.
4. **Severity:** S5 (Note)
5. **Location:** `tests/acceptance/sdk-recovery.mjs:45-71`; evidence contract in `tests/acceptance/support/stack.mjs:113-149` and `tests/acceptance/README.md:8-12`
6. **Expected:** An evidence entry presented as an assertion should derive `passed` from an independently observed result and compare that result with an expected contract. Phase timing and test parameters should be explicit metadata or a separately named telemetry stream.
7. **Actual:** The `timeline()` helper always passes `passed: true` (`sdk-recovery.mjs:45-53`) and is called once for the baseline plus eight times per recovery cycle (`:96`, `:227-494`). It has no expected value or failure predicate, so every reached milestone is an unconditional pass. The `recovery scenario parameters` entry (`:55-71`) copies `recoveryCycles` and all timeout constants into both `expected` and `actual`, then hard-codes `passed: true`; apart from `run_id`, it proves only what this test invocation was configured to do. At the default one cycle, the timeline alone contributes nine non-assertive entries; at the permitted five-cycle maximum it contributes 41.
8. **Reproduction:**
   1. Inspect `tests/acceptance/sdk-recovery.mjs:45-71`; neither `passed` field can become false, and the parameter `expected` values are the same constants used to construct `actual`.
   2. Count the timeline call sites at `:96` and `:227`, `:235`, `:255`, `:268`, `:281`, `:398`, `:443`, and `:494`. `parseRecoveryCycles()` permits one through five cycles at `:803-810`, producing 9 or 41 unconditional timeline records respectively.
   3. Run the scenario with `ATLAS_ACCEPTANCE_ARTIFACTS=<artifact-dir>` and inspect `evidence.jsonl`; the milestone and parameter entries have `passed: true` while the behavior assertions later in the same file compute `passed` from SDK observations (`:209-226`, `:291-344`, `:367-396`, and `:506-524`).
9. **Notes:** This is a test-evidence maintenance issue, not a false-green product defect. `record()` fails on `passed: false` (`support/stack.mjs:118-147`), and the recovery scenario's substantive checks remain observation-based; removing or relabeling these entries would not change the scenario's pass/fail behavior. The source report's broader count is not reproducible at this revision: `rg -n -U 'passed:\s*true' tests/acceptance --glob '*.mjs'` finds 15 textual occurrences, but only six are direct hard-coded record objects. The other nine are seven expected assertion fixtures (`simulations/observations-objects.mjs:969-990` and `simulations/multi-client-sync.mjs:911-937`), one Promise result (`sdk-recovery.mjs:241`), and one expected field (`sdk-recovery.mjs:264`). The fixture values are compared with independent simulation output (`simulations/src/scenarios/observations-objects.ts:160-195` and `simulations/src/scenarios/multi-client-sync.ts:107-128`), so they are not padding records. The alleged duplicate readiness record is also false: `support/stack.mjs:515-520` returns after a successful HTTP 200, while `:526-532` records only the mutually exclusive timeout failure; `:216` is the sole success record.
