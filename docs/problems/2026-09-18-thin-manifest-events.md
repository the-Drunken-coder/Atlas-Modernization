1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** Runtime-manifest entity events are thin notifications, forcing hand-rolled refetch coherence in the command interface
3. **Issue:** When an Asset runtime becomes ready, Core emits an entity `update` event with `change_reason: runtime_manifest_changed` but no manifest payload; every consumer that needs the manifest must fetch the Asset detail again, and the command interface carries the entire refetch/coherence burden in surface code.
4. **Severity:** S4
5. **Location:** services/core/internal/actions/task_runtime.go:307-334, 336-354; services/core/internal/actions/change_hook.go:129-176; services/core/internal/actions/entity_actions.go:41-44; surfaces/command-interface/src/features/MapConsole.tsx:144-255; surfaces/command-interface/src/atlas/data-source.ts:96-135, 370-397
6. **Expected:** Per the 2026-06-12 fat-events decision (docs/design-decisions/2026-06-12-change-feed-websocket-fat-events.md §5: "Thin notifications force follow-up reads and ordering races"), entity update events should carry enough after-state for consumers to act without follow-up reads. A manifest-change event should therefore include the new ready manifest, or the SDK should provide a read-through detail cache, so no per-interface refetch state machine is needed.
7. **Actual:** resourceChangeRecord (change_hook.go:147-153) serializes only the raw Entity record via SerializeEntity; the manifest is not part of the Entity JSON blob (services/core/docs/database-structure/entities.md:88) and lives in the separate `asset_runtimes` table (task_runtime.go:280, 336-354), joined solely by EntityActions.GetDetail (entity_actions.go:41). The event ends up as a pure notification: it advances the entity version so consumers "can then refetch the detail" (task_runtime.go:308). The command interface pays for this: MapConsole.tsx keeps a mutable `EntityDetailsRequest` ref (inFlight/cancelled/retryAfterVersion/staleRefreshAttempts and a self-referencing `start()`) coordinated by two useEffects across ~112 lines to dedupe, retry on stale versions, and re-trigger when the manifest version moves; data-source.ts maintains a parallel `runtimeManifestVersions` map from raw events (data-source.ts:96-112, 370-382) plus a hydration-vs-event ordering workaround `runtimeManifestVersionsAfterHydration` (data-source.ts:115-121, 384-397).
8. **Reproduction:** Source trace: task_runtime.go:280 writes manifest to `asset_runtimes`, then :283 calls recordRuntimeManifestEntityChange; :315-319 advances only the entities row (no manifest join); :323-332 records ChangeEventUpdate/ChangeResourceEntity with ChangeReason runtime_manifest_changed and AfterEntity; change_hook.go:153 sets `event.Resource = serializers.SerializeEntity(change.AfterEntity)` — the serialized entity has no `command_manifest` because it is not in the entity JSON. Feed consumers (SDK sync) see the version bump but no payload. MapConsole.tsx:158-223 builds the details request; :225-255's second effect watches the snapshot version and the refetched details and calls `request.start()` again at :254; data-source.ts:100-107 detects `runtime_manifest_changed` builds the version map; data-source.ts:384-397 re-derives those versions from hydration snapshots to cover the event/hydration ordering gap.
9. **Notes:** This is a deliberate, documented invariant break with a stated rationale: task_runtime.go:307-309 says the manifest stays out of the event to avoid "duplicating the manifest outside the authoritative runtime record," and docs/atlas-change-feed/README.md:25 codifies `runtime_manifest_changed` as a thin signal — the only allowed change-reason, invalid on other event variants. The engines.md/entities.md constraint that `command_manifest` is read-only join data further supports keeping Core duplication minimal. The cost is real but concentrated in the interface: the refetch state machine in MapConsole.tsx (two coordinated effects, stale-version retry counter, retryAfterVersion gating) and the version-map/hydration logic in data-source.ts exist solely to recover the manifest from these thin events, above an SDK that already does cache coherence and gap recovery. Fix directions: (a) attach the ready manifest to the feed event resource for change_reason `runtime_manifest_changed` (the join is one SELECT against asset_runtimes at write time; the manifest is already validated/encoded at task_runtime.go:280), noting the durable-log size consequence of duplicating manifests per event; (b) give the SDK a read-through entity-detail cache keyed on entity version so the interface refetch is automatic; (c) at minimum, move the runtimeManifestVersions tracking into the SDK so data-source.ts and MapConsole.tsx shed the parallel coherence layers. Evaluation: directions (a) and (b) trade server-side simplicity vs client-side deletion directly against the fat-events decision's reasoning; (b) is the least invasive and matches the "clients still use version guards" consequence in the decision, while (a) is the most consistent with it.
