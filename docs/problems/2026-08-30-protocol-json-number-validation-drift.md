# Problem Report

1. **Time & Date:** 2026-08-30T14:59:08Z
2. **Name:** Protocol integer validation loses exact JSON number semantics
3. **Issue:** The Protocol Go validator normalizes each `json.Number` to `int64` when possible and otherwise to `float64`. That conversion rounds large or fractional values and underflows tiny exponents before the JSON Schema integer check. Consequently, the validator can accept a wire number that the generated Go `int64` type cannot decode. The generated TypeScript predicate also accepts integers above JavaScript's safe-integer limit, so it cannot preserve their value exactly.
4. **Severity:** S3 (Moderate)
5. **Location:** `packages/protocol/validator/validator.go:274-294`, `packages/protocol/schema/jsonschema/atlas.schema.json:684-699,733-736`, `packages/protocol/generated/go/atlasprotocol/types.go:516-519`, `packages/protocol/generated/typescript/index.ts:708-710`, `packages/sdk/src/validation.ts:105-110`
6. **Expected:** Canonical-schema validation, generated Go decoding, and generated TypeScript predicates should agree on accepted integer wire values. A value accepted as an integer should remain exact and be representable by the generated consumers, or validation should reject it with a clear error.
7. **Actual:** `ValidateFeedSubscriptionsReadyMessage` returns no errors for `9223372036854775808` (above `int64`), `9223372036854775807.5` (rounded by `Float64` to an integer), and `1e-4000` (underflowed by `Float64` to zero). `json.Unmarshal` of each value into `FeedSubscriptionsReadyMessage.Version int64` fails. It also accepts `1.0`, which the JSON Schema treats as mathematically integral but the generated Go `int64` decoder rejects. The generated TypeScript predicate and SDK inbound predicate accept values such as `9007199254740993` and `9223372036854775808` after JavaScript rounds them, without a `Number.isSafeInteger` check.
8. **Reproduction:**
   1. From `packages/protocol`, call `validator.ValidateDefinition("FeedSubscriptionsReadyMessage", map[string]any{"type":"subscriptions_ready", "version":json.Number(raw)})` or the generated `ValidateFeedSubscriptionsReadyMessage` with a `json.RawMessage`, using `raw` values `9223372036854775808`, `9223372036854775807.5`, `1e-4000`, and `1.0`. The result is `[]` for each.
   2. Unmarshal the corresponding payload, for example `{"type":"subscriptions_ready","version":9223372036854775808}`, into `atlasprotocol.FeedSubscriptionsReadyMessage`. Go returns `cannot unmarshal number ... into Go struct field FeedSubscriptionsReadyMessage.version of type int64`; the same happens for the fractional, underflowed, and `1.0` payloads.
   3. Run `node_modules/.bin/tsx -e 'import { isFeedSubscriptionsReadyMessage } from "./packages/protocol/generated/typescript/index.ts"; import { isInboundFeedSubscriptionsReady } from "./packages/sdk/src/validation.ts"; for (const raw of ["9007199254740993","9223372036854775808"]) { const value=JSON.parse(`{"type":"subscriptions_ready","version":${raw}}`); console.log(raw, value.version, isFeedSubscriptionsReadyMessage(value), isInboundFeedSubscriptionsReady(value)); }'`. Both predicates return `true`, while JavaScript prints rounded values (`9007199254740992` and `9223372036854776000`).
9. **Notes:** The focused Go probe was run against detached HEAD `804bf32fa733ca582f931816f58cdb5aae218701`; no repository files were changed by the investigation. The existing protocol test intentionally confirms that `1.0` is valid under JSON Schema integer semantics (`packages/protocol/protocoltest/validators_test.go:176-178`), which makes the Go decoder mismatch observable. The smallest repair must preserve numeric lexemes through validation or explicitly constrain the schema and generated consumers to one representable range; generated artifacts should be regenerated from the canonical schema rather than edited directly. Add cross-language cases for out-of-range integers, large fractions that round to integers, tiny exponents, `1.0`, and unsafe JavaScript integers.
