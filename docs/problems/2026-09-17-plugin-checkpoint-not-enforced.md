# Problem: Core release packaging does not advance the Plugin catalog checkpoint

1. **Time & Date:** 2026-09-17T11:38:07-04:00 America/New_York
2. **Name:** Core releases retain a stale embedded Plugin catalog checkpoint
3. **Issue:** The Plugin release contract requires each Atlas Core release to embed the newest authenticated `(key_epoch, sequence)` catalog pair verified during the build. The checked-in Core trust file remains at checkpoint `1/1`, while the independent Plugin publication workflow can advance the signed catalog independently.
4. **Severity:** S3 (Moderate)
5. **Location:** `surfaces/core-cli/assets/plugin-trust.json:1-17`; `docs/atlas-plugins/RELEASE_FORMAT.md:220-228`; `.github/workflows/release-atlas-core.yml:329-360,914-949`; `surfaces/core-cli/scripts/generate-package-metadata.mjs:1-36`
6. **Expected:** A Core release build should obtain and verify the current signed catalog, then update the release artifact's embedded `minimum_checkpoint` to that authenticated pair before the package is reviewed and packed. The release artifact should not rely on a hand-maintained older checkpoint.
7. **Actual:** `plugin-trust.json` embeds `minimum_checkpoint` `{ "key_epoch": 1, "sequence": 1 }`. The Core release workflow versions the package, runs checks, and packs it, but does not read or update `plugin-trust.json` (`release-atlas-core.yml:329-360,914-949`). The package metadata generator only reads `package.json` and the generated Protocol revision (`generate-package-metadata.mjs:5-20,22-36`). The separate Plugin workflow appends and publishes catalog sequences from its protected ledger (`release-atlas-plugin.yml:420-459`) without feeding the resulting checkpoint back into a Core release.
8. **Reproduction:**
   1. Inspect `surfaces/core-cli/assets/plugin-trust.json`; its embedded checkpoint is `key_epoch=1, sequence=1`.
   2. Inspect `docs/atlas-plugins/RELEASE_FORMAT.md:220-228`; it requires each Core release to embed the newest verified pair.
   3. Trace the Core release preparation and packaging steps in `.github/workflows/release-atlas-core.yml:329-360,914-949`; no step fetches, verifies, or writes a catalog checkpoint.
   4. Trace `surfaces/core-cli/scripts/generate-package-metadata.mjs`; it has no catalog or trust input and writes only package/version/image/Protocol metadata.
   5. Install a fresh Core package whose catalog endpoint still serves a valid catalog at sequence 1 after a later revocation has advanced the published catalog. `verifyCatalog()` accepts that sequence because it compares against the stale embedded checkpoint (`surfaces/core-cli/src/plugin-distribution.ts:271-281`), so the fresh install can replay the older still-valid catalog until its expiry.
9. **Notes:** The checkpoint enforcement itself is implemented and tested: a catalog below the configured checkpoint is rejected (`surfaces/core-cli/src/plugin-distribution.ts:274-277`; `surfaces/core-cli/test/plugin-distribution.test.ts:352-363`). The defect is that the Core release pipeline never advances the configured checkpoint. The frozen finding recorded the published catalog at sequence 2; a live Pages fetch was attempted during this verification but DNS/network access was unavailable, so the current public sequence should be rechecked before implementation. Existing installations retain their stronger local receipt, making the replay exposure primarily a fresh-install or reset path as described by the release contract.
