2. **Name:** Admin endpoint wire shapes are hand-written in Go and TypeScript with no protocol-schema source of truth or parity gate
3. **Issue:** Admin resource shapes (login request, user/me response, API-key request/response) exist as two independently maintained copies (Go handler structs, TS SDK types) while every resource endpoint is schema-generated and drift-checked in both directions.
4. **Severity:** S4
5. **Location:** `services/core/internal/api/handlers/handler_admin_auth.go:13-25`, `services/core/internal/api/handlers/handler_admin_api_keys.go:13-28`, `packages/sdk/src/admin.ts:11-39`
6. **Expected:** Admin wire shapes should follow the same pipeline as the rest of the contract: authored in `packages/protocol/schema/jsonschema/atlas.schema.json`, with generated Go types/validators and generated TS types/predicates, and covered by the conformance drift check that the protocol module exists to provide.
7. **Actual:** `grep -ric admin` on `atlas.schema.json` returns 0 matches and `packages/protocol/generated/go/atlasprotocol/types.go` has no Admin types. The six admin shapes are hand-written on both sides with nothing asserting the two copies stay in sync; a field rename or type change on one side fails only at runtime (and TS-side runtime fails only via the hand-rolled predicates in `admin.ts:71-105`).
8. **Reproduction:**

   - Go: `adminLoginRequest` {username, password} (`handler_admin_auth.go:13`), `adminUserResponse` {username, expires_at,omitempty} (`:18`), `adminMeResponse` {user} (`:23`), `adminCreateAPIKeyRequest` {name} (`handler_admin_api_keys.go:13`), `adminAPIKeyResponse` {id, name, key_prefix, created_at, created_by} (`:17`), `adminCreateAPIKeyResponse` = embed + api_key (`:25`).
   - TS: `AdminLoginRequest` (`admin.ts:20`), `AdminUser` (`:11`), `AdminMeResponse` (`:16`), `AdminCreateAPIKeyRequest` (`:33`), `AdminAPIKey` (`:25`), `AdminCreatedAPIKey` (`:37`) mirror them by hand.
   - Parity coverage check: `packages/protocol/conformance/request-validation.json` and `request_validation.go` contain no admin cases; `services/core/internal/integration/request_conformance_test.go` covers entity/object/tasking only; `packages/sdk/test/http-client.test.ts` and `url.test.ts` assert AtlasAdminClient routes/credentials exist, never field-level shape parity with the Go structs.
9. **Notes:** (a) Field-by-field status as of 2026-09-18: fully in sync — login {username,password}; user {username, expires_at?}; me {user}; api-key create req {name}; api-key {id,name,key_prefix,created_at,created_by}; created-key = api-key + {api_key}. No current drift; the risk is latent. Semantics do differ subtly: Go emits `expires_at` via `omitempty` + RFC3339, and TS accepts any non-empty string for it (`admin.ts:76`) or `created_at`/`created_by`, so the TS guards are weaker than a generated validator would be. (b) Documented intent: `docs/atlas-protocol/README.md:13` enumerates the implemented contract's scope (Entity, Task, Object, command catalog, runtime, queries, errors, feed) and admin is simply absent; no doc anywhere states admin endpoints are intentionally outside the protocol, so this is an unrecorded gap, not a deliberate carve-out. (c) Separation claim verified: `packages/sdk/src/protocol.ts:83,134` re-exports types from `../../protocol/generated/typescript/index.js`, and `packages/sdk/src/client.ts:4-20` builds the main AtlasClient on those generated types; because admin shapes have no generated types to share, `AtlasAdminClient` (`admin.ts:41`) must duplicate the transport and hand-rolled guards as a second client. If admin shapes were added to the schema and generated, `admin.ts` could collapse into generated types/predicates and the admin methods could live on the main client, matching the other resources.
