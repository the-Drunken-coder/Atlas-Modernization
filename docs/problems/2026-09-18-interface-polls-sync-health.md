1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** Command interface polls the SDK's pull-only `status()` on a 3s interval instead of watching an event-driven health update
3. **Issue:** The connection badge (MapConsole.tsx:671 → ConnectionBadge) can lag up to 3 seconds behind health transitions the SyncEngine knows instantly, and the interface maintains a hand-written field-by-field dedupe to make the polling tolerable. The interval also keeps running (wakeups every 3s) even while healthy — a trivial but nonzero battery/CPU cost on an event-driven system.
4. **Severity:** S4
5. **Location:** surfaces/command-interface/src/state/atlas-context.tsx (healthTimer at line 72, publishHealth dedupe at lines 95–117, `setInterval(poll, 3000)` at lines 163–170); SDK gap in packages/sdk/src/sync-engine.ts (`status()` at lines 207–216 is pull-only; `watchSnapshot` at lines 222–226 shows the push precedent; no status watcher exists)
6. **Expected:** A `watchStatus(callback)` (or equivalent) on SyncEngine that pushes health transitions the moment `this.health` changes, mirroring `watchSnapshot`. The interface would subscribe once and delete both the `setInterval` poll and the manual dedupe (push callbacks only fire on change, so identity-stable publishing comes for free).
7. **Actual:** `SyncEngine.status()` is pull-only; the SDK offers no way to observe health changes. atlas-context.tsx:169 compensates with `setInterval(poll, 3000)` reading `dataSource.health()` (data-source.ts:153–164 → `client.sync.status()`), and publishHealth (atlas-context.tsx:95–117) manually compares `running`/`healthy`/`degraded`/`error.source`/`error.message` field-by-field to avoid context-value churn on every tick.
8. **Reproduction:** Trace health transitions inside the engine: `this.health = "degraded"` is set synchronously at sync-engine.ts:309 (feed event error), 318 (feed close), 326 (feed connection failed), 351 (recovery start), 367 (recovery request failed), 598, 610, 731, 799, 845, 854; recovery to healthy happens in `markSynchronized` at 879. None of these notify any listener — `status()` (207–216) just projects `this.health` on read. The only consumers are the 3s interval in atlas-context.tsx:163–170 (immediate `poll()` at 168, then `healthTimer = setInterval(poll, 3000)` at 169) feeding `publishHealth`. So a drop to degraded is reflected on the badge up to 3s later; likewise recovery. The interval runs unconditionally after startup regardless of health state. No React state subscription to `sync.status()` exists anywhere (grep of surfaces/command-interface/src shows `status()` only called inside data-source.ts pull paths at lines 91, 114, 154), so the interval is not redundant with any push path — there is no push path for status.
9. **Notes:** `watchSnapshot` (sync-engine.ts:222–226) is the in-tree precedent: a watcher set plus an unsubscribe closure; `watchStatus` would follow the same pattern and be invoked wherever `this.health` is assigned (or in a small `setHealth` helper). Dedupe inventory that a watcher deletes: (a) publishHealth's five-field comparison, atlas-context.tsx:99–107, plus the error-retain/clear logic at 108–116; (b) a second hand-written dedupe in the snapshot path, data-source.ts:124 (`next.entities === previous.entities && next.tasks === previous.tasks`), which exists for the same reason — no change-notification granularity — though a snapshot watcher fix is a separate concern. Cost check: the 3s interval is cheap (one synchronous status projection per tick) but runs forever while the surface is mounted, including when the tab is backgrounded (setInterval throttling mitigates but does not eliminate it).
