# Problem: CLI lifecycle coverage stops at a mocked caller seam

1. **Time & Date:** 2026-09-17T11:38:13-04:00
2. **Name:** Meshtastic `serve` test does not exercise the real lifecycle wiring
3. **Issue:** `cli-lifecycle.test.ts` is useful caller-plumbing coverage, but its module mock replaces `startLinkService` and its radio fixture is an empty type assertion. Consequently, no test currently executes the production `serve` caller together with the real lifecycle implementation and a radio-shaped fixture.
4. **Severity:** S5 (Note)
5. **Location:** `packages/meshtastic-link/src/cli-lifecycle.test.ts:8-25,35-90`; production call site `packages/meshtastic-link/src/cli.ts:126-152`; real lifecycle `packages/meshtastic-link/src/lifecycle.ts:44-180`
6. **Expected:** Keep the focused caller test, but clearly pair it with one thin CLI-to-lifecycle wiring test (or an equivalent explicit acceptance check) that uses the real `startLinkService` and a concrete fake radio. The test suite should distinguish option-plumbing coverage from lifecycle-construction and startup/cleanup coverage.
7. **Actual:** The test mocks both lifecycle exports at lines 14-17 and the radio class at lines 19-25. Its first test creates `const radio = {} as MeshtasticSerialRadio` (line 43), then the mocked `startLinkService` only calls `options.openRadio()` (lines 47-50) and returns a fabricated address/`close`. Therefore `startLinkService` never constructs `LinkRadioGate`, `RadioProfileManager`, `LinkService`, or `LinkHTTPServer`, never performs profile/membership startup, and never runs lifecycle cleanup. The real lifecycle tests (`lifecycle.test.ts:19-163`) and compiled process acceptance runner (`acceptance/process-runner.ts:69-101`) cover the implementation directly, but neither invokes `cli.ts`'s `serve` path. A regression in the CLI's real lifecycle import/wiring or in the option shape required by actual startup could therefore leave this CLI test green.
8. **Reproduction:**
   1. Inspect `cli-lifecycle.test.ts:14-17`; importing `cli.ts` resolves `startLinkService` to `mocks.startLinkService`, not `lifecycle.ts`'s implementation.
   2. Follow the first test at lines 43-50. The only radio interaction is the mocked factory returning `{}`; no radio method is available or called.
   3. Follow `cli.ts:135-151`. Production `serve` would call the real lifecycle and eventually need the radio methods used by `lifecycle.ts` (for example `rawRadio.nodeNumber()` at line 131 and profile adapter operations), but this test substitutes a fake running service before any of those operations can occur.
   4. Confirm the separate lifecycle coverage calls `startLinkService` directly (`lifecycle.test.ts:33-40,73-81,102-110,142-149`) and the process runner does the same (`acceptance/process-runner.ts:80-87`); there is no `main(["serve", ...])` test without the lifecycle mock.
9. **Notes:** This is not evidence of a current production failure, and the existing test is correctly valuable for defaults, argument validation, radio-factory invocation, readiness output, and caller-owned close behavior. The gap is limited to integration/wiring confidence and is best treated as a small maintenance note. The focused test could not run in this checkout: with Node 24, `npm test --workspace @the-drunken-coder/atlas-meshtastic-link -- --run src/cli-lifecycle.test.ts` stopped in `pretest` because `node_modules/@meshtastic/core/package.json` is absent. `git diff --check` passed.
