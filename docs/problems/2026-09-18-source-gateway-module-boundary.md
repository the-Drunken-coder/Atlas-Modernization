1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** Source Gateway is a separate deployable trapped inside the Core Go module with no ownership slot
3. **Issue:** `cmd/atlas_source_gateway` + `internal/sourcegateway` (~1,900 LOC non-test) ship as their own container with independent config, HTTP surface, healthcheck, and failure domain, yet they share Core's `go.mod`, release cadence, and `internal/` visibility boundary; neither `AGENTS.md` nor the deployment-layout decision defines a place for a second hosted service inside `services/core`.
4. **Severity:** S5
5. **Location:** `services/core/cmd/atlas_source_gateway/main.go`, `services/core/internal/sourcegateway/{gateway.go,config.go,wire.go}`, `services/core/go.mod`, `services/core/docker/docker-compose.production.yml:54`, `services/core/docker/Dockerfile:33,75,122-133`, `AGENTS.md:23`, `docs/design-decisions/2026-08-27-deployment-shaped-repository-layout.md`
6. **Expected:** A service that is deployed, configured, health-checked, and failure-isolated independently of Core should live at its own module/root (e.g. `services/source-gateway/`) or be explicitly accepted as a Core subsystem in the repository-layout decision and `AGENTS.md`.
7. **Actual:** The Gateway compiles only inside the `github.com/the-drunken-coder/atlas/services/core` module; its package sits under Core's `internal/` (invisible to any future separate module), builds from the same Dockerfile builder stage and dependency set, and is deployed as a distinct container that the documented architecture treats as an independent failure domain. `AGENTS.md:23` says "`services/` is centrally hosted software" but the layout decision enumerates `services/core` as the only concrete services root — the Gateway has no slot and is neither promoted nor accepted.
8. **Reproduction:** (a) `head -1 services/core/go.mod` → single module `.../services/core` containing both binaries. (b) `docker-compose.production.yml:54-70` defines `source-gateway` as a separate container (`atlas_core_production_source_gateway`) with its own config volume (`ATLAS_SOURCE_GATEWAY_CONFIG`), healthcheck, and network; `Dockerfile:33` builds `./cmd/atlas_source_gateway` as its own binary with production stage at line 122. (c) `grep -rn "internal/sourcegateway" services/core --include=*.go` shows exactly one importer: `cmd/atlas_source_gateway/main.go:15` — no Core code (`cmd/atlas_core`, `internal/httpapi`, etc.) imports it; the only outbound dependency is `internal/sourcegateway/config.go:17` importing Core's `internal/pluginid`. (d) `docs/design-decisions/2026-08-25-source-gateway-hosts-source-connectors.md` line 6: "One private Source Gateway container hosts named Source connectors"; line 8 (Consequences): "Gateway failure degrades source-dependent Plugins without changing Core liveness or readiness."
9. **Notes:** Design-decision citation verified: the 2026-08-25 decision explicitly mandates a separate container and failure isolation ("Gateway failure … without changing Core liveness or readiness"), and it references circuit-breaker state as Gateway-owned. The failure-isolation is implemented in software too: `gateway.go:60-92` carries a fully custom circuit breaker (`breakerSerial`, `breakerAttempts`, `breakerFailures`, `breakerCredits`, `lastReachable`, `breakerHistoryLimit`) with no shared Core dependency. Import direction is one-way (gateway → `internal/pluginid`); Core never imports `internal/sourcegateway`, so promotion to a sibling module is mechanically cheap — the `pluginid` import would need to move to a shared package. Deployment separation is already real (own container, config file, healthcheck, Dockerfile stages); the genuine problem is the module/ownership boundary, not the container split. The boundary ambiguity is structural: any future change that needs the Gateway package outside the Core module (or any reader applying `AGENTS.md`'s services rule) has no documented answer.
