1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** SDK initial hydration downloads the entire dataset unconditionally; subscriptions never scope it
3. **Issue:** `sync.start()` pages through every Entity, Task, and object via `/queries/full` before connecting to the feed, regardless of subscription filters; with permanent Task retention, every client's startup payload grows without ceiling.
4. **Severity:** S3 (growth/degradation on a core path with no workaround; not a current outage)
5. **Location:** `packages/sdk/src/sync-engine.ts` (lines 586-589, 668-673, 694-724, 924-926), `packages/sdk/src/cache.ts` (lines 273-296), `services/core/internal/api/handlers/handler_query_parsing.go` (lines 88-110), `services/core/internal/actions/query_actions.go` (lines 24-109), `services/core/internal/feed/hub.go` (lines 242-249), `surfaces/command-interface/src/atlas/data-source.ts` (line 56), `docs/design-decisions/2026-06-10-deferred-core-reshapes.md`
6. **Expected:** Hydration should respect the client's subscription set (or otherwise bound what a client downloads), so per-client startup cost stays proportional to what that client consumes. Operators using the command interface should not each load the full dataset.
7. **Actual:** `startSyncFromStopped` calls `hydrate` unconditionally (sync-engine.ts:589). `fetchAndInstallHydratedSnapshot` (sync-engine.ts:694-724) loops `GET /queries/full` following `entity_cursor`/`task_cursor`/`object_cursor` and accumulates every entity, task, and object into arrays, then `cache.replaceHydratedResources` (cache.ts:273-296) clears all three caches and accepts every returned resource. No code path consults `this.subscriptions` during hydration. Core's `/queries/full` accepts only `entity_limit`/`task_limit`/`object_limit` and cursors (handler_query_parsing.go:88-110); `GetFullDataset` selects all rows per type (query_actions.go:24-109). Subscription filters only gate the websocket feed: the SDK sends them to the feed (feed-connection.ts:299-302) and Core's hub filters live events via `subscriptionMatches` (hub.go:242-249). Tasks are retained permanently by design (`docs/design-decisions/2026-06-10-deferred-core-reshapes.md`, "permanent Task retention"; `docs/atlas-protocol/commands-and-tasking.md` line 34), so the task stream is append-only. The command interface constructs its client with `sync: "all"` (data-source.ts:56), so every operator hydrates the whole dataset on login.
8. **Reproduction:** 1. Start dev Atlas Core with a dataset of K entities/tasks/objects. 2. Load the command interface (or create an SDK client with `sync: "all"` and call `start()`), observing the network tab: repeated `GET /queries/full?entity_cursor=...` requests page through all K resources. 3. Before `start()`, call `client.subscribe()` with a narrow filter (e.g. a single entity id) — step 2's traffic is unchanged, because hydration never reads the subscription set. Note also that `sync: false` does not avoid this: `start()` → `startSyncFromStopped` → `hydrate` runs regardless of `initialSync` (sync-engine.ts:174-189, 589).
9. **Notes:** Disproof attempts all failed: `fullDatasetPath` (sync-engine.ts:924-926) carries only cursor params; `FullDatasetCursors` (types.ts:162) has no filter fields; `parseFullDatasetLimits` has no content filter; `replaceHydratedResources` unconditionally accepts all resources. The feed genuinely does filter by subscription, so the gap is specifically hydration plus permanent task retention. Fix likely needs either server-side filtered hydration (a filterable snapshot endpoint) or SDK-side hydration scoped to subscriptions; the paging/`assertPaginationProgress`/version-watermark machinery in `fetchAndInstallHydratedSnapshot` is orthogonal and can be reused. Related: `sync: false` currently only skips the pre-registered `{filter:"all"}` subscription, not hydration itself.
