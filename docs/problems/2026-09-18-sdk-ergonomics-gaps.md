1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** SDK mixes 10-positional-arg internals and inconsistent cancel-signal support; object upload absent but not duplicated in tests
3. **Issue:** The SDK's internal call layer passes up to 10 positional arguments with runs of `undefined` placeholders, and cancel-signal support is inconsistent across client methods — updates, deletes, and all query helpers accept no signal while the rest of the surface does. Object upload is genuinely absent from the SDK, but no test currently hand-rolls it, so the duplication cost claimed in the review does not exist today.
4. **Severity:** S5
5. **Location:** `packages/sdk/src/sync-engine.ts:485-496`, `packages/sdk/src/sync-engine.ts:511-517`, `packages/sdk/src/http.ts:123-133`, `packages/sdk/src/http.ts:183-195`, `packages/sdk/src/client.ts:123-198`, `packages/sdk/src/client.ts:322-372`, `packages/sdk/src/types.ts:38-115`, `docs/atlas-sdk/README.md:27`, `docs/atlas-sdk/README.md:138`
6. **Expected:** Internal transport/engine methods should take a single options object (the pattern `writeTask` at `sync-engine.ts:430` and `deleteResource` at `sync-engine.ts:540` already use), and cancel-signal support should be uniform across all client methods that issue HTTP requests, including `entities.update`, `objects.update`, `entities.delete`, `objects.delete`, `queries.full`, `queries.changedSince`, `commandCatalog`, and `objects.content`.
7. **Actual:** `writeResource` takes 10 positional parameters, forcing call sites like `entities.create` (`client.ts:134-135`) and `objects.create` (`client.ts:333-334`) to pass `undefined, undefined` placeholders; `transport.json` takes 7 positional parameters with the same runs (`client.ts:163-164`, `client.ts:376`, `http.ts:185`). Signal support is split: `get`/`create`/`delete`-adjacent task/runtime/plugin/check-in/movement methods accept `options.signal`, while `update` options are inline `{ ifMatchVersion?: number }` (`client.ts:140`, `client.ts:339`), `ResourceDeleteOptions` has only `instanceToken` (`types.ts:48-50`), `FullDatasetQueryOptions` and `ChangedSinceQueryOptions` have no signal field (`types.ts:103-110`, `types.ts:112-115`), and `commandCatalog`/`objects.content` take no signal at all (`client.ts:371-372`, `client.ts:355`). Object upload exists only as Core's multipart `POST /objects/upload` (`services/core/internal/api/handlers/handler_object_transfer.go:144`) with no SDK wrapper, which the docs acknowledge as a deliberate deferral.
8. **Reproduction:** Read `packages/sdk/src/sync-engine.ts:485-496` — `writeResource(method, path, body, type, expectedID, validate, ifMatchVersion?, eventName?, signal?, requestHeaders?)` is 10 positional params; read `packages/sdk/src/client.ts:127-138` — `entities.create` calls it with `undefined, undefined` in positions 7-8; same at `client.ts:326-337` for `objects.create`; `client.ts:376` calls `transport.json("GET", "/plugins", isPluginDiscoveryResponse, undefined, undefined, options?.signal)`; `http.ts:185` calls `raw(method, path, undefined, undefined, requestSignal)`. For signal inconsistency: compare `types.ts:43-46` (`ResourceCreateOptions` has `signal`) against `types.ts:48-50` (`ResourceDeleteOptions` does not) and `types.ts:103-110` (`FullDatasetQueryOptions` does not); `client.ts:361-362` (`queries.full`) passes no signal to `transport.json`; `client.ts:140` update options carry only `ifMatchVersion`. For upload: `grep -rn -i "upload" packages/sdk/src surfaces simulations --include=*.ts` returns zero consumer-side hits; the `objects` namespace (`client.ts:322-358`) exposes only get/create/update/delete/content/watch, where content is download-only (`client.ts:492` hits `GET /objects/:id/download`).
9. **Notes:** Sub-claim verification: (1) 10-positional-param method with `undefined, undefined` call sites — CONFIRMED as above; max param count is exactly 10 (`writeResource`), and the same module already demonstrates the options-object style in `writeTask` (`sync-engine.ts:430`) and `deleteResource` (`sync-engine.ts:540`), so the two styles coexist internally. (2) Signal inconsistency — CONFIRMED with full enumeration above; specifically, `queries.full` was checked and does NOT include a signal: `FullDatasetQueryOptions` (`types.ts:103-110`) has only limit/cursor fields and the call site passes none, so the original caution resolved in the finding's favor. (3) Upload absent from SDK — CONFIRMED; "tests write their own upload code" — NOT CONFIRMED: `grep -rn -i "upload\|FormData\|multipart"` across `packages/sdk/test`, `surfaces/`, `simulations/`, and `services/core/internal/integration/` finds no hand-rolled upload in any test; the only upload code is Core's own server implementation and its handler tests (`handler_object_transfer.go`, `internal/actions/object_upload.go`), which is server-side testing of the endpoint, not consumer duplication. This absence of demonstrated duplication cost is why severity is S5 rather than S4. (4) Docs acknowledge the gap — CONFIRMED at `docs/atlas-sdk/README.md:27` ("Object upload remains a direct API call for now") and `:138` ("Upload remains a direct Core API call for now; the SDK already has the transport and cache conventions it should follow when this is added"), making the upload portion a documented deferral rather than an undiscovered defect; the live ergonomic inconsistency (positional args, signal coverage) is the actionable part.
