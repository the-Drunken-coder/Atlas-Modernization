# Stale SDK feed delete can clear a pending local delete

1. **Time & Date:** 2026-07-30T08:33:00Z
2. **Original Audit Finding:** 4
3. **Validation Status:** Confirmed against `main` at `2426bb6`.
4. **Name:** Stale SDK feed delete can clear a pending local delete
5. **Affected Surface & Severity:** Atlas SDK synchronized cache and watchers; S2 (Major). The failure is an SDK-cache resurrection, not a resurrection in Atlas Core's durable state.
6. **Current vs. Expected:** After a successful local delete, `ResourceCache.markLocalDelete` records a tombstone at the previously cached version and adds the resource key to `pendingDeletes`. `SyncEngine.applyEvent` handles any feed delete while that key is pending before its normal version guard: it clears `pendingDeletes` and overwrites the tombstone with the event's version. A delayed delete at or below the cached version can therefore remove the pending protection, after which a changed-since resource at a later version is accepted by `applyRecoveredEvent` and appears live again. A stale delete should be ignored by the version guard without clearing the pending marker; only a delete newer than the local tombstone should acknowledge it.
7. **Concrete Source Evidence:** `atlas_sdk/src/cache.ts:186-203` stores the previous resource version in the local tombstone and sets `pendingDeletes`. `atlas_sdk/src/sync-engine.ts:573-588` clears that marker for a pending feed delete before `atlas_sdk/src/sync-engine.ts:593-596` checks `event.version <= versionFor(...)`. `atlas_sdk/src/sync-engine.ts:612-632` then accepts a later recovered resource once the pending marker is gone. Existing coverage at `atlas_sdk/test/sync-engine-reconnect-cleanup.test.ts:434-477` protects pending deletes from stale **updates**, but there is no equivalent stale-delete regression.
8. **Reproduction / Static Proof:** A focused temporary Vitest regression passed as a reproduction on Node 25.9.0 and Vitest 4.1.10: hydrate entity version 1; delete it (Core commits delete version 2 while the SDK records a pending local tombstone at version 1); emit a delayed feed delete at version 1; return a changed-since entity at version 2; call `client.changedSince()`; then `client.entities.get(id)` resolves to the version-2 entity with alias `resurrected`. The command was `vitest run atlas-stale-delete.test.ts --root /tmp --environment node`; one test passed. The decisive ordering is also visible statically: the pending-delete branch at lines 579-588 is reachable before the version guard at lines 593-596.
9. **Root Cause:** The pending-delete acknowledgement branch assumes every matching feed delete is the committed delete corresponding to the local request, even though delayed events from an earlier version are valid feed input.
10. **Simplest Correct Proposed Solution:** Apply the per-resource version guard before mutating `pendingDeletes`, `locallyNotifiedDeletes`, or the tombstone. Preserve the existing acknowledgement behavior only for a delete whose version is newer than the local tombstone. Do not add a compatibility path or a second delete state machine.
11. **Acceptance Criteria / Regression-Test Plan:** Add a focused SDK regression that reproduces the version-1 local tombstone, stale version-1 feed delete, and version-2 recovered entity sequence and asserts the entity remains deleted with only the original `local_delete` notification. Also retain a control showing that a newer feed delete clears the pending marker without a duplicate notification, and keep the existing stale-update and later-recreation tests passing.
12. **Scope / Non-Goals:** Do not change Atlas Core delete semantics, invent client-generated delete versions, or prevent a genuinely later Core recreation from replacing a completed tombstone.
13. **Overlaps:** Related to finding 7 because both involve feed correctness, but this problem is deterministic event ordering inside one SDK cache, not server queue overflow. It is distinct from finding 2, which concerns durable object upload/delete races in Core.
