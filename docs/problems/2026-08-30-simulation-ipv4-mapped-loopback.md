1. **Time & Date:** 2026-08-30T15:00:42Z
2. **Name:** Simulation host checks misclassify IPv4-mapped IPv6 loopback
3. **Issue:** Simulation URL and request-host classification recognizes `127.0.0.0/8` and `::1` but not IPv4-mapped IPv6 loopback addresses. Node's URL parser canonicalizes `https://[::ffff:127.0.0.1]` to `https://[::ffff:7f00:1]`, which the exact-string checks treat as a deployed host rather than loopback.
4. **Severity:** S4 (Minor)
5. **Location:** `simulations/src/server/config.ts`, `simulations/src/server/http-utils.ts`, and `simulations/src/server/cleanup-ledger.ts`
6. **Expected:** An IPv4-mapped IPv6 address whose IPv4 value is in `127.0.0.0/8` should be treated as loopback consistently. A mapped loopback URL should be accepted as a local simulation target, rejected as a deployed target, and its loopback Host header should pass the local UI trust check.
7. **Actual:** `isLoopbackHost` in `config.ts` compares the URL hostname only with `localhost`, `::1`, or a dotted-decimal `127.*` value. For `https://[::ffff:127.0.0.1]:8000`, `isDeployedAtlasUrl` returns `true`; `loadConfig` rejects the URL as a local target, but accepts it as an explicitly enabled deployed target. `hasLoopbackHost` in `http-utils.ts` makes the same exact-string comparison, so a request using the canonical Host header `[::ffff:7f00:1]:5180` is rejected with the non-loopback Host policy. The cleanup-ledger target validation consequently also accepts the mapped loopback URL as a deployed target.
8. **Reproduction:**
   1. From `simulations/`, run this focused source probe (it uses no live Core or external state):
      `node --import tsx --input-type=module -e 'import { isDeployedAtlasUrl, loadConfig } from "./src/server/config.ts"; import { hasLoopbackHost } from "./src/server/http-utils.ts"; const input="https://[::ffff:127.0.0.1]:8000"; let localError=""; try { loadConfig({ env: { ATLAS_LOCAL_BASE_URL: input }, packageRoot: "/tmp" }); } catch (error) { localError=error instanceof Error ? error.message : String(error); } const deployed=loadConfig({ env: { ATLAS_SIM_ENABLE_DEPLOYED: "true", ATLAS_DEPLOYED_BASE_URL: input }, packageRoot: "/tmp" }); console.log(JSON.stringify({ canonical: new URL(input).href, isDeployed: isDeployedAtlasUrl(input), localError, deployedTarget: deployed.atlasTargets[1], trustedHost: hasLoopbackHost(new URL(input).host) }));'`
   2. Observe canonicalization to `https://[::ffff:7f00:1]:8000/`, `isDeployed: true`, the local-target error `ATLAS_LOCAL_BASE_URL must target loopback`, a populated deployed target, and `trustedHost: false`. The same probe reports `false` for `isDeployedAtlasUrl("http://[::1]:8000")` and `true` for its trusted Host check, demonstrating the intended comparison.
9. **Notes:** This is a deterministic source probe; no live server was contacted and no product code or tests were changed. The practical impact is a broken edge-case configuration and an unnecessary deployed-mutation confirmation requirement, with ordinary `localhost`, `127.0.0.1`, and `::1` workarounds. The smallest fix is to parse IPv6 addresses and recognize IPv4-mapped values whose embedded IPv4 address is loopback, then share that predicate between URL and request-host validation. Add focused cases for `::ffff:127.0.0.1`, canonical `::ffff:7f00:1`, non-loopback mapped addresses, and the equivalent Host header; preserve the requirement that ordinary private non-loopback addresses remain deployed.
