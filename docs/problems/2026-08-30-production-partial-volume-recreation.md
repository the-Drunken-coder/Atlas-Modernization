# Problem

1. **Time & Date:** 2026-08-30T14:54:17Z
2. **Name:** Production launcher recreates a missing PostgreSQL volume beside retained MinIO data
3. **Issue:** The manual production launcher starts Docker Compose without checking that PostgreSQL and MinIO durable volumes are present as a matched pair. If PostgreSQL storage is lost while MinIO remains, Compose creates a new empty PostgreSQL volume and the launcher can report a healthy production stack beside stale object blobs.
4. **Severity:** S1 (Blocker)
5. **Location:** `services/core/scripts/atlas.py`, `services/core/docker/docker-compose.production.yml`, `services/core/docker/docker-compose.production-db.yml`
6. **Expected:** Production startup must fail closed when either durable store is missing or cannot be proved to belong to the same deployment. Operators should restore the paired PostgreSQL/MinIO backup or explicitly initialize a new deployment before any container starts.
7. **Actual:** `start_containers(production=True)` calls `cleanup_containers()` at `services/core/scripts/atlas.py:717-723`, which runs `docker compose down --remove-orphans` without `--volumes`, and then immediately runs `docker compose ... up -d --build` at `services/core/scripts/atlas.py:741-747`. There is no volume existence or pairing check. The production Compose model declares ordinary, non-external named volumes at `services/core/docker/docker-compose.production.yml:122-126` (and the PostgreSQL-only model does the same at `docker-compose.production-db.yml:28-30`), so Compose creates `atlas_core_production_postgres_data` when it is absent. The new PostgreSQL instance initializes an empty database; Core's startup calls `EnsureTables` at `services/core/cmd/atlas_core/main.go:138-148`, while `minio-init` only verifies the retained configured bucket with `mc stat` at `docker-compose.production.yml:98-118`. If that bucket and its old blobs remain, the API can pass readiness with a fresh metadata database and retained object storage that no longer corresponds to it.
8. **Reproduction:**
   1. Configure valid production credentials, including `POSTGRES_PASSWORD`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`, `API_AUTH_KEY`, and `ATLAS_ADMIN_PASSWORD`.
   2. In the `atlas_core_production` Compose project, arrange for `atlas_core_production_minio_data` and its configured bucket/objects to remain while `atlas_core_production_postgres_data` is absent. This represents PostgreSQL volume loss or an incomplete restore; do not perform this against a real deployment.
   3. Run `python3 services/core/scripts/atlas.py --production`.
   4. Observe from the launcher source path that it performs no Docker volume inspection between `down` and `up`. `docker compose config` confirms both are ordinary local named volumes with no `external: true`; Docker Compose therefore creates the missing PostgreSQL volume during `up`.
   5. The new PostgreSQL database is healthy and Core applies its schema. The retained MinIO bucket passes `minio-init` and Core's durable bucket check, allowing `/readiness` to become healthy even though the database rows and object blobs are from different store generations.

9. **Notes:**
   - Safe checks on this checkout (`804bf32fa733ca582f931816f58cdb5aae218701`) reproduced the launcher call sequence with `subprocess.run` mocked: the only Docker call issued by the production start path was `docker compose --project-name atlas_core_production -f docker-compose.production.yml up -d --build`; no `docker volume inspect`, `docker volume ls`, or paired-store guard was called.
   - `docker compose ... config --volumes` returned `postgres_data` and `minio_data`, and rendered configuration showed the resolved ordinary volumes `atlas_core_production_postgres_data` and `atlas_core_production_minio_data` with no external-volume requirement. No containers, volumes, or production resources were touched.
   - The published `atlas-core` CLI has a separate start guard in `surfaces/core-cli/src/application.ts:776-797`, but that does not protect operators using the documented `services/core/scripts/atlas.py --production` launcher.
   - The repository's deployment documentation explicitly says PostgreSQL and MinIO are one logical durable store and must be restored together (`services/core/docs/DATABASE_WORKFLOW.md:14`, `services/core/docs/DEPLOYMENT_RUNBOOK.md:5`).
   - Smallest safe fix: add a production preflight that inspects both Compose-owned volumes and refuses startup on a partial pair; use explicit external volumes or a recorded installation identity so Compose cannot silently create a replacement. Add mocked launcher tests for missing PostgreSQL and missing MinIO, plus a non-destructive Compose configuration assertion.
