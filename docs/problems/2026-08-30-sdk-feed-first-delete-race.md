1. **Time & Date:** 2026-08-30T10:56:15-04:00
2. **Name:** SDK applies a feed-first delete twice and hides a racing recreation
3. **Issue:** An SDK local delete records its cache marker only after the HTTP DELETE resolves. If Core's versioned delete event arrives first, the SDK notifies the remote delete, then marks the already-deleted resource as a local delete when the HTTP response arrives. A same-ID create delivered between those two moments is subsequently removed from the snapshot by the late local marker.
4. **Severity:** S3 (Moderate)
5. **Location:** Atlas SDK, `packages/sdk/src/sync-engine.ts` (`deleteResource` and `applyEvent`) and `packages/sdk/src/cache.ts` (`markLocalDelete`)
6. **Expected:** A successful local DELETE should produce one effective delete transition. If Core's versioned delete has already been applied, the later HTTP response should not emit `local_delete` or leave a pending local-delete marker. A newer same-ID create must remain visible and deliver its create event.
7. **Actual:** `deleteResource` waits for `transport.empty` at `sync-engine.ts:541-543` before calling `markLocalDelete`. A feed-first delete therefore takes the unmarked branch at `sync-engine.ts:849-858`, notifies `delete`, and records the versioned tombstone. The HTTP response then calls `markLocalDelete` at `cache.ts:200-207`, notifies `local_delete` at `sync-engine.ts:544`, and re-adds `pendingDeletes` and `locallyNotifiedDeletes`. If a newer create was applied during the response delay, `cacheResource` initially makes it visible and clears those markers, but the late `markLocalDelete` removes it again. The watcher receives `delete`, `create`, and `local_delete`; the snapshot omits the recreated resource and the markers remain pending.
8. **Reproduction:**
   1. Start an SDK client with `sync: "all"`, a WebSocket feed, and a watcher for `entity:asset-recreated`; hydrate an existing entity.
   2. Wrap `fetch` so `DELETE /entities/asset-recreated` calls the Core delete, delivers its committed delete event to the client's WebSocket, and holds the successful HTTP response unresolved.
   3. Before releasing the response, recreate the same entity ID in Core and deliver its newer `create` event to the client's WebSocket.
   4. Release the held DELETE response and await `client.entities.delete("asset-recreated")`.
   5. Observe watcher events in this order: `delete`, `create`, `local_delete`. `client.sync.snapshot().entities["asset-recreated"]` is absent, and the SDK cache contains the `pendingDeletes` and `locallyNotifiedDeletes` key `["entity", "asset-recreated"]`.
   6. A focused Vitest reproduction of both the feed-first double notification and the hidden recreation passed with `./node_modules/.bin/vitest run --root /private/tmp --environment node /private/tmp/sdk-delete-race.test.ts` (2 tests passed; temporary test file outside the repository).
9. **Notes:** The documented watch contract says `local_delete` is for a successful local DELETE that removes the resource before Core's versioned delete arrives (`docs/atlas-sdk/README.md:62`); the change-feed contract requires newer events to supersede older tombstones (`docs/atlas-change-feed/README.md:60`). The smallest fix is to establish an in-flight delete marker before issuing HTTP, then reconcile the response with the already-applied delete/create version rather than unconditionally calling `markLocalDelete`; add a gated feed-first delete test with same-ID recreation and assert one final visible create.
