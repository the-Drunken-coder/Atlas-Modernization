1. **Time & Date:** 2026-09-17T15:27:01Z
2. **Name:** Pull-request acceptance workflows have no changed-path gate
3. **Issue:** The current pull-request workflow set schedules its acceptance and package checks for every pull request, including documentation-only changes, without a `paths` or `paths-ignore` filter. The expensive acceptance paths then perform disposable Docker setup and dependency/image downloads even when their code cannot have changed.
4. **Severity:** S4 (Minor)
5. **Location:** `.github/workflows/*.yml`; `tests/acceptance/support/stack.mjs:41-75,174-213`; `.github/workflows/ci.yml:163-215`; `.github/workflows/integration.yml:35-75`
6. **Expected:** Documentation-only or otherwise unrelated pull requests should retain the lightweight checks that protect documentation and workflow changes while skipping acceptance jobs whose covered package and fixtures did not change. Any checks required by branch protection need an explicit aggregate result so filtering does not leave a required check pending.
7. **Actual:** Twenty-two workflow files currently declare `pull_request` without a path filter. The acceptance runner used by the browser, SDK, simulation, and Plugin scenarios always runs `docker compose build` and then pulls `postgres`, `minio`, and `minio-init` (`tests/acceptance/support/stack.mjs:174-213`); the integration workflow starts a rebuilt Core Compose stack on every matching pull request (`.github/workflows/integration.yml:35-75`). Six workflow files directly install Playwright, with browser matrices producing eight installer executions on a normal pull-request event (`.github/workflows/browser-acceptance.yml:17-45`; `browser-commands.yml:20-43`; `browser-geofeatures.yml:26-52`; `browser-map-windows.yml:16-42`; `simulation-browser-acceptance.yml:17-45`; `ci.yml:163-196`). The original report's “eighteen Docker/Playwright workflows” count is therefore not accurate, but the avoidable setup is real.
8. **Reproduction:**
   1. Check out `43b5928ceba19bc95d00d578cc6ed9c03319167e` and enumerate the pull-request workflows lacking a path gate:
      `for f in .github/workflows/*.yml; do if rg -q '^  pull_request:' "$f" && ! rg -q '^    paths(-ignore)?:' "$f"; then echo "$f"; fi; done`
      This prints 22 workflow files.
   2. Open a pull request targeting `main` whose only change is under `docs/`. Each of those 22 workflow files remains eligible because its pull-request trigger has no changed-path condition.
   3. In any acceptance job backed by `runAcceptance` (for example `node tests/acceptance/plugins/reference/scenario.mjs`), trace `runPluginAcceptance` into `runAcceptance`; observe the unconditional Compose build and dependency pulls at `tests/acceptance/support/stack.mjs:199-212`.
   4. For the browser jobs, observe the unconditional `npm ci` and Playwright installer steps in the workflow files listed above. These jobs do not inspect the changed paths before allocating their runner and download time.
9. **Notes:** This is a CI maintenance/cost defect, not a product correctness failure. The source trace proves the work is scheduled; no current GitHub billing-duration sample was available because the live `gh api` request failed to connect, so the reported “50–60 runner-minutes” is not retained as a measured figure. The historical Reference Plugin Alpine `apk` TLS failure is also not independently reproducible here: the local Docker daemon is unavailable, although the path remains externally sensitive because `services/core/docker/Dockerfile:122-123` runs `apk upgrade` and `apk add` during the Reference stack's source-gateway build. Do not add raw path filters without checking required-status behavior; use a changed-path classifier or aggregate check where necessary.
