1. **Time & Date:** 2026-09-18T15:00:56Z
2. **Name:** Geofeature delete from UI is permanently gated on a browser-local token that Core never requires
3. **Issue:** The command interface only offers geofeature deletion when it holds the create-time `Atlas-Resource-Instance-Token` in browser localStorage, but Core accepts the same DELETE with no token at all. Clearing browser storage or deleting from a different browser/machine removes the UI delete control permanently, with no recovery path because Core stores only a hash of the token.
4. **Severity:** S3 (broken edge case with painful workaround: the geofeature becomes undeletable from the UI after localStorage loss or a machine switch; deletion is still possible only by issuing a raw Core API call outside the UI)
5. **Location:**
   - `services/core/internal/api/handlers/handler_entity.go:155-168` (DELETE route parses token; nil when header absent)
   - `services/core/internal/api/handlers/handler_preconditions.go:21-36` (absent header → `nil, true`)
   - `services/core/internal/actions/entity_actions.go:519-529` (token check runs only `if deleteOptions.InstanceToken != nil`; delete proceeds at :551)
   - `services/core/internal/actions/resource_instance_token.go:13-15,39-45` (header const; sha256-only storage)
   - `services/core/internal/database/migrations.go:268-275` (`resource_instance_tokens.token_hash`, 64-char hash columns)
   - `surfaces/command-interface/src/atlas/data-source.ts:251-257` (`canDeleteGeofeature`/`deleteGeofeature` refuse without retained token), :302-303 (localStorage key `atlas:geofeature-instance:<baseUrl>:<entityId>`), :187 (token generated client-side via `crypto.randomUUID()`)
   - `surfaces/command-interface/src/features/geofeatures/use-geofeature-delete.ts:32-33` (`available` gates on `canDeleteGeofeature`)

6. **Expected:** Any operator who can view a geofeature in the command interface can delete it. Create-time instance tokens exist for create retry-safety; they should not gate destructive deletes in the UI, and they certainly should not make deletion impossible after a browser storage change. (The token check for deletes is optional in Core — the UI could simply omit it, matching the SDK's optional `instanceToken`.)
7. **Actual:** `canDeleteGeofeature` returns false and `deleteGeofeature` throws "Geo Feature deletion is unavailable" unless the exact browser holds the token recorded at create time under `atlas:geofeature-instance:<baseUrl>:<entityId>` in localStorage. MapConsole then renders the inspector with no delete control at all, with no explanation. Because Core stores only `sha256(token)` (`resource_instance_tokens.token_hash`, `entities.instance_token_hash`) and no API returns the plaintext token, the UI can never recover it; the geofeature is undeletable from any fresh browser forever, even though Core would accept the identical DELETE request with no token header.
8. **Reproduction:**
   1. In browser A, open the command interface and create a geofeature (the UI generates `crypto.randomUUID()` and retains it in localStorage).
   2. In browser B (or after clearing site data in browser A, or on another machine), open the command interface against the same Core and select the geofeature.
   3. Observe the inspector offers no delete control (`deletion.available(...)` is false because `tokenFor(entityId)` finds no localStorage entry).
   4. Confirm via the Core API that `DELETE /entities/{entity_id}` with no `Atlas-Resource-Instance-Token` header returns 204 — Core deletes the resource fine without any token, proving the block is purely the UI's token gate.
9. **Notes:** Verified current behavior, not hypothetical: `EntityActions.Delete` skips the precondition when `InstanceToken == nil` (entity_actions.go:519), and existing Core tests already call `Delete(ctx, id)` with nil options expecting success (e.g. `query_changed_since_test.go:112`, `task_lifecycle_test.go:654`, `write_version_concurrency_test.go:41`). Go suites could not be re-run in this environment (no Go toolchain installed); the 41 data-source and 59 MapConsole vitest suites pass and encode the gating (`data-source.test.ts:582-594`: `canDeleteGeofeature` true with retained token, false after it is forgotten). Core stores only `sha256(token_hash)` in the `resource_instance_tokens` table and `instance_token_hash` columns, so the plaintext token exists solely in the creating browser — recovery from Core is impossible by design. Fix direction: stop using the instance token as a delete permission. For create retry-safety prefer a server-visible `Idempotency-Key` (as already used for tasks), and for deletes use conditional requests (`If-Match` with the entity's strong ETag/version), which Core already parses (`handler_preconditions.go:12-19,38-103`); the SDK's optional `ResourceDeleteOptions.instanceToken` and Core's nil-token path mean the UI fix is to stop requiring the token rather than to add recovery machinery.
