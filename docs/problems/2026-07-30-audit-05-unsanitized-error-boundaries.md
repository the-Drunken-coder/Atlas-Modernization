# Audit 05: error sanitization is incomplete across operator-facing boundaries

1. **Time & Date:** 2026-07-30T18:00:00-07:00
2. **Original Audit Number:** 5
3. **Validation Status:** Partially confirmed against `main` at `2426bb6`.
4. **Name:** Error sanitization is incomplete across operator-facing boundaries
5. **Affected Surface & Severity:** Atlas Command Interface, Atlas SDK/CLI, and Atlas Simulations; **S1 (Blocker)** because a server, transport, or callback error can disclose credentials or emit terminal control characters. The original claim is too broad for connection/bootstrap errors, which are already sanitized.
6. **Issue:** The repository has a comprehensive `sanitizeConnectionError` implementation and uses it at connection and authentication-shell boundaries, but several mutation, simulation, SDK, and terminal boundaries still surface raw `Error.message` or server `message` text.
7. **Current vs Expected:**
   - **Current:** Command-interface connection/bootstrap/session/logout errors are redacted, single-line, control-character filtered, and length-bounded. Command submission, geometry-save, API-key administration, and some map-runtime errors are copied directly into React state. The SDK constructs `AtlasAPIError.message` from the Core response's raw `message`; the CLI writes that message directly to stderr. Simulations only byte-bound error text before persisting it in run summaries/events, returning it over HTTP/SSE, rendering it in the UI, or writing startup failures to the terminal.
   - **Expected:** Every untrusted error is sanitized once before it crosses into a UI, durable/operator-visible run record, HTTP/SSE response, or terminal/log sink. Structured sensitive fields, URL userinfo, sensitive query parameters, known Atlas keys, bare bearer tokens, newlines, and terminal control sequences must be removed. Structured error identity such as status and `error_code` should remain available separately.
8. **Concrete Source Evidence:**
   - Protected command-interface boundaries: `atlas_command_interface/src/atlas/connection-error.ts:1-129`; `atlas_command_interface/src/app/providers.tsx:23-29,55-61`; `atlas_command_interface/src/auth/ui/AuthGate.tsx:33-36,117-125,173-175,209-218`; `atlas_command_interface/src/state/atlas-context.tsx:86-96,121-130,156-161`; and the defense-in-depth pass in `atlas_command_interface/src/ui/ConnectionBadge.tsx:17-26`.
   - Unprotected command-interface boundaries: command submission and geometry save in `atlas_command_interface/src/features/MapConsole.tsx:150-168,227-236`; API-key list/create/revoke failures in `atlas_command_interface/src/features/admin/APIKeysPanel.tsx:38-43,63-66,92-95,164-166`; and raw map-runtime messages in `atlas_command_interface/src/ui/map/view/MapView.tsx:121-138,198-205`.
   - SDK source boundary: `atlas_sdk/src/http.ts:93-100,131-157` incorporates the raw Core `message` into the public exception and retains the full response. Terminal sinks are `atlas_sdk/src/cli.ts:89-108` and the watch-callback console sink at `atlas_sdk/src/sync-engine.ts:740-744`. CLI success/watch JSON is not part of the terminal-control finding because `JSON.stringify` escapes control characters.
   - Simulation boundaries: `atlas_simulations/src/server/run-store-events.ts:68-95,121-132` truncates but does not redact; `atlas_simulations/src/server/run-store-execution.ts:58-77,87-103` copies raw failures into `lastError`, error events, and terminal status; cleanup does the same in `atlas_simulations/src/server/run-store-cleanup.ts:37-78,155-159`; `atlas_simulations/src/client/api.ts:128-149,321-324` propagates transport/server messages; and `atlas_simulations/src/client/App.tsx:219-222` plus `AppPanels.tsx:35-43,104-113` render them. `atlas_simulations/src/server/index.ts:299-305` writes startup errors directly to a terminal.
9. **Reproduction / Static Proof:**
   1. Run `rg -n 'sanitizeConnectionError|cause instanceof Error \\? cause\\.message|error instanceof Error \\? error\\.message|io\\.stderr\\.write|console\\.error' atlas_command_interface/src atlas_sdk/src atlas_simulations/src`.
   2. For the protected path, pass `Error("https://user:pass@core.test?api_key=atlas_ak_secret\\nnext")` to `sanitizeConnectionError`; existing `connection-error.test.ts` asserts redaction/control filtering for this family.
   3. For an unprotected SDK/CLI path, return `{ "error_code": "BAD", "message": "Authorization: Bearer secret\u001b[31m" }` from a fake non-OK fetch. `HttpTransport` embeds it unchanged and `runCLI` writes it unchanged to stderr.
   4. For simulations, throw an error containing `api_key=atlas_ak_secret` from a scenario/client operation. `executeRun` stores it in `run.lastError` and emits it; the browser renders the same text. The only transformation is byte truncation.
10. **Root Cause:** Sanitization was implemented specifically for Core connection health and later reused by the auth/bootstrap shell, but no shared trust-boundary policy covers mutation errors, SDK public errors, simulations, and terminal sinks. Length bounding in simulations was treated as sufficient despite solving a different problem.
11. **Simplest Correct Proposed Solution:** Move the existing sanitizer into a small exported Atlas SDK utility, then import it from the command interface and simulations, which already depend on the SDK. Invoke it at each operator-display/log boundary. Preserve raw structured payloads only for explicit programmatic inspection and never print them implicitly. Keep React's text rendering; this is disclosure/control-sequence hardening, not HTML escaping.
12. **Acceptance Criteria / Regression-Test Plan:**
   - Table-driven tests cover structured fields, URL userinfo, encoded/camel-case query keys, bare bearer tokens, `atlas_ak_` keys, CR/LF, C0/C1/ANSI sequences, and length bounds.
   - Command submit/save and API-key failures show redacted messages while retaining 401 handling.
   - Simulation summaries, SSE events, UI banners/log rows, cleanup errors, and server console output contain no supplied canary secret or terminal escape.
   - SDK `AtlasAPIError` preserves status/`errorCode`; CLI stderr contains no canary secret or control sequence.
   - Existing connection-error tests remain green, proving already-safe boundaries do not regress.
13. **Scope / Non-Goals:** Do not hide generated API keys in the successful one-time API-key creation UI; that display is intentional. Do not sanitize ordinary resource data or JSON CLI stdout. Do not redesign error taxonomy or logging infrastructure beyond the trust boundary needed here.
14. **Overlaps:** Finding 17 can introduce credential-bearing base URLs that later appear in errors. Finding 31 concerns error strings as SDK control flow, a separate typed-discriminator problem. Finding 16's Python scripts also print raw HTTP response bodies, but their recommended removal is documented separately.
