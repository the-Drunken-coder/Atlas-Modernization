Atlas Protocol

The foundational contract layer for Atlas — one definition of what the data is.

Direction · implemented slices active

Atlas Protocol is a central, foundational package that lives outside Atlas Core and above it. It owns the data structures and the rules for verifying them. The implemented slices have moved those rules out of handwritten Core-only copies and into a generated source of truth that other packages can project from.

01Why this exists

The shape of an entity, task, or object, and the rules for a valid component (telemetry, geometry, media_refs roles, RFC3339 timestamps, command objects) now have a protocol home for the implemented slices. Remaining handwritten docs and future projections still need to stay aligned so downstream consumers — notably the frontend — can rely on the same JSON shapes.

02What we want it to do

Be the single source of truth for the data model

Define entities, tasks, objects, and their components once, with their constraints, in one place.

Generate code instead of us hand-writing it

Produce Go types and validators from the definitions so Atlas Core's handwritten validation and known-key tables become generated artifacts, not maintained-by-hand copies.

Give every language the same contract

One definition → Go for the backend, TypeScript for the frontend, and (optionally) OpenAPI for the HTTP surface. The frontend stops guessing.

Push verification to the edges

The same schema can back app-level validation and a database boundary (JSON Schema → Postgres checks), so integrity no longer depends on every writer going through one Go code path.

Detect generated drift

A generated revision stamp or content hash tells us whether checked-in artifacts were produced from the current JSON Schema source. It is a freshness check, not backwards-compatible protocol versioning.

03The boundary that keeps it clean

The protocol defines shape and contract. Atlas Core keeps behavior. If the protocol ever imports a database driver or knows about HTTP, the line has been crossed.

Protocol owns

  • Data structures & field types
  • Valid component keys & enums
  • Constraints (ranges, formats, required)
  • Cross-language type generation
  • Generated artifact freshness

Core keeps

  • Transactions & row locking
  • Merge semantics & read-modify-write
  • Task lifecycle / status transitions
  • Auth, HTTP, storage wiring
  • Pagination & query execution

04How we're growing into it

Incrementally, lowest-risk first — this is a sliced implementation, not a big-bang rewrite:

  • Generate Core-facing validators and TypeScript artifacts from the protocol definitions.
  • Keep behavior (merge logic, lifecycle, transactions) handwritten in Core.
  • Add the TypeScript projection after the Go validator path stays stable.
  • Consider database-level validation after the contract has settled.

05Current status

  • Implemented slices: entity, task, and object blobs; entity and task components; object references; telemetry; and geometry.
  • Generated-code workflow: output is checked in and never hand-edited; the protocol check command fails when artifacts drift from JSON Schema.
  • Deferred work: OpenAPI fragments, database checks, and HTTP request/response envelope contracts.
Scope note: as Atlas Protocol grows, project-level decisions and blockers move with it. Design decisions and problems now live at the project root (docs/design-decisions/, docs/problems/) precisely because they span Atlas Core, Atlas Protocol, and whatever comes next — they are no longer Core-only.
